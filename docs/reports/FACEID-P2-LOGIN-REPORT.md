| 项 | 结果 |

## 二、登录链路（`Controllers/FaceIdController.cs` → `Services/FaceId/FaceIdLoginService.cs`）

控制器只管"这一步该不该继续"，识别本身在 `FaceIdLoginService`（不签票、不写审计、不改账号状态，纯识别）。

| 顺序 | 分支 | 返回 | 为什么必须在这个位置 |
|---|---|---|---|
| 1 | 用户名为空 | 400 `EMPTY_FIELDS` | 不值得开摄像头 |
| 2 | 用户不存在 | 401 `FACEID_MISMATCH` | **与"人脸不像"完全一致**，否则登录页就成了用户名字典 |
| 3 | 账号 `Locked` | 401 `ACCOUNT_LOCKED` | **在采脸之前**：已锁定的账号不该再拿到一次识别机会 |
| 4 | 账号 `Disabled` | 403 `ACCOUNT_DISABLED` | 同上 |
| 5 | 采集 + 逐张过质量闸门 + 与模板取最大余弦 | 三途判定 | 见 `FaceIdDecision` |
| 6 | 通过 | 200 + 票据 | `ResetFailedAttempts` + `LastLoginAt` + `IssueAsync` |
| 7 | 未通过 | 401 + `similarity` | 只有 `IsCounted` 为真的码才进失败窗口 |

要点：

- **相似度回传给界面**。本人看到 `0.83 还差一点` 就知道是光线问题，`0.12` 说明脸根本不对。这不构成可用攻击信息 —— 本来就能反复试，而每次试都在审计里。
- **`ResetFailedAttempts` 只在成功时调用**，与口令登录同一个出口，不另写一套清零逻辑。
- **审计字段锁死**：哈希链输入字段是固定的，`SecondFactor=FACEID` 只能塞进 `response` JSON 袋（落库是**字符串**，断言前要 `parse_bag`）。

## 三、计次规则：码决定分组，调用点不自己判断

| 码 | 计次 | 理由 |
|---|---|---|
| `FACEID_MISMATCH` | ✅ | 明确不是本人，与口令错同级 |
| `FACEID_LIVENESS_FAILED` | ✅ | 举照片属于主动尝试（默认活体关闭，只有显式开启时才会出现） |
| `FACEID_NOT_ENROLLED` | ❌ | 账号根本没录过脸，不是"试错"，计次只会把用户越锁越死 |
| `FACEID_GRAY_ZONE` | ❌ | 把握不足，等于让"今天灯太暗"逐步把本人锁在门外 |
| 质量类（没人脸/多脸/太小/侧脸/糊） | ❌ | 与 2FA 侧同一套分流（`FaceCodes.IsCounted` 的对照） |
| 引擎不可用（503） | ❌ | 环境问题，不是用户的错 |

## 四、前端：登录页第三个页签

- 页签栏变成 **登录 / 人脸登录 / 注册** 三个，`AppIcon name="face"`。
- 表单只有一个输入框（用户名）+ 一句说明"点击后会打开摄像头识别一次（约 1–3 秒）"，**不传图像、不传特征**（与录入同一条边界）。
- 失败时把相似度拼进提示：`err.message（相似度 0.412）`，便于用户区分"光线"与"脸不对"。
- 原有「口令登录 / 注册 / 找回密码」流程**一行未改**。

> 这一条正是用户 10-19 实测反馈：「鲍喜顺账号录入纯人脸登录后退出，登录页没有单独的纯人脸登录选项」。
> 后端 P1a 就已存在，缺的是**入口**。

## 五、新建账号的初始口令固定为 `Abc12345`

**问题**：原表单并排有两个口令框（"初始口令"与"您的登录口令"），很容易把管理员**自己的**口令填进"初始口令" ⇒ 新账号的密码等于管理员密码，一次填反就把管理员凭据交了出去。

**改法**：删除"初始口令"输入框，改为**只读展示**固定值 `Abc12345`，提交时硬编码这个常量。

- `Abc12345` 8 位、含大小写与数字 ⇒ 满足后端复杂度裁决（`IS_PASSWORD_COMPLEX`），**不需要为"固定口令"在后端开例外分支**（那条例外迟早会被别处复用）。
- **代价必须写在界面上**：初始口令是公开的约定值，任何知道用户名的人都能在本人改密之前登进来。所以提示语明确写了"创建后请让本人登录并立即修改"。
- **后端仍接受调用方指定的口令**。没有改成"服务端强制覆盖"：既有接口语义与全部探针（角色 92 / 锁定 40 / 人脸 93）都依赖"调用方指定口令再登录"，强改会把它们全部打断。这一条是**界面层修正**，不是服务端控制，口径上不能混。

### ⚠️ 一个把"判错"测成"通过"的坑

J 组首轮 72/75：`backend()` 默认注入 `AUTHBASELINE_FACEID_STUB_IDENTITY=<探针用户>`，
**同一身份**算出来的特征余弦恒为 1.0 ⇒ 「人脸判错」永远返回 200。
更糟的是"审计记 `FACEID_MISMATCH`"这条断言当时用的是**全局计数**，被前一组"不存在的账号"凑出了 1，看起来是绿的。

修法两条：① 判错组显式换 `AUTHBASELINE_FACEID_STUB_IDENTITY=stranger-identity`；② 断言改成**本组恰好多 1 条**（`n=1→2`）。

## 七、口径（别说满）

1. **这不是"刷脸即登录"的通用能力**：唯一因子登录本身弱于"口令 + 人脸"，本项目把它做成**账号级可选**，代价由用户自己承担。
2. **相似度阈值仍是起点值**（0.50 / 灰区 0.05），没有定档。LFW 上 96.83% 的 acc 是**离线基线**，不能当成线上通过率。
3. **活体默认关闭**（验收要手举照片），意味着默认状态下"照片即本人"。界面与启动日志都如实标注，**不许说成"有活体防护"**。
4. 初始口令固定是**界面层**修正，服务端不阻止管理员用 API 指定别的口令。
