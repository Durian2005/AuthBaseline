# FaceId 侧 SFace 通过线标定

- 日期：2026-10-24
- 地位：阶段 2（SFace AND）落地前的**前置标定**，回答"0.50 这个数能不能直接用"
- 结论：**不能。FaceId 侧的 SFace 通过线应定 0.46，不是 2FA 的 0.50。**
- 脚本：`.workbuddy/tmp/faceid-quant/sface_threshold.py`（LFW 侧）、`sface_hard_negative_sweep.py`（撞脸侧）
- 数据：LFW（本机 `.workbuddy/tmp/lfw/`，不入库）+ `tools/fixtures/faceid-quant/`（19 张，gitignore）

---

## 一、问题：为什么不能直接搬 0.50

阶段 0 的"撞脸 0/4"是在 **SFace@0.50** 下算出来的，而 0.50 是 **2FA 的通过线**。两个模块的安全目标不同：

| | 2FA 人脸 | FaceId 纯人脸登录 |
|---|---|---|
| 位置 | 第二因子，后面还有口令 | **唯一凭证** |
| 该线调高一点 | 多一次验证失败 | **本人进不去系统** |
| 该线调低一点 | 少一道保险，口令仍在 | 可能被冒充 |

所以在 2FA 上"严一点更安全"，在 FaceId 上"过严 = 可用性事故"。**阈值必须按 FaceId 的目标重定，不能继承。**

---

## 二、方法：两个方向夹出可行区间

单看 LFW 定不了这条线 —— LFW 的负样本是"两个普通不同人"，本来就容易分；真正决定 SFace 该多高的是**撞脸对**。所以两边各出一半约束：

| 方向 | 数据 | 回答 | 给出 |
|---|---|---|---|
| **上限** | LFW 1500 正 + 1500 负对 | 再高就会让**普通人**进不来 | 阈值上限 |
| **下限** | 19 张真实素材（撞脸 4 / 双胞胎 3 / 本人 2） | 再低就会让**撞脸**混进来 | 阈值下限 |

LFW 侧的配对、种子、参考管线**全部复用 `tools/faceid_lfw_eval.py`**，与 P0 那份 96.83% 基线同源。

### 自校验：管线没跑偏

| 指标 | 本次 | P0 报告 |
|---|---|---|
| ArcFace EER | **1.87%** | **1.87%** |
| 正样本对 / 负样本对 | 1500 / 1500 | 1500 / 1500 |
| 缓存图片 | 3612 张 | — |

EER 逐位一致 ⇒ 这批分数就是 P0 那批评分。配方自检另有硬闸门：脚本先用 30 张图把"我这条 ArcFace 分支"与 `py_embed` 对比，最小余弦 < 0.9999 直接中止。

## 三、LFW 侧：0.50 到底贵在哪

固定 ArcFace@0.30（现行 FaceId 通过线），扫 SFace 阈值，**AND 是同一对同时过线的实测联合**，不是独立相乘的估计：

| SFace 阈值 | SFace 单独 TAR | SFace 单独 FAR | AND 的 TAR | 相对 ArcFace 单独 | AND 的 FAR |
|---|---|---|---|---|---|
| （ArcFace 单独） | — | — | **97.87%** | — | 0/1500 |
| 0.40 | 97.53% | 0.133% | 97.47% | −0.40pp | 0/1500 |
| 0.44 | 96.67% | 0.067% | 96.67% | −1.20pp | 0/1500 |
| 0.45 | 96.40% | 0.067% | 96.40% | −1.47pp | 0/1500 |
| **0.46** | 95.87% | **0.000%** | **95.87%** | **−2.00pp** | **0/1500** |
| 0.48 | 94.60% | 0.000% | 94.60% | −3.27pp | 0/1500 |
| **0.50（2FA 线）** | 92.67% | 0.000% | **92.67%** | **−5.20pp** | 0/1500 |
| 0.55 | 87.27% | 0.000% | 87.27% | −10.60pp | 0/1500 |

**这张表是本次标定最有用的一行结论：0.50 让本人通过率白掉 5.2 个百分点。**

对照 P3 定档的动机——当时把阈值语义修正后，本人被拒率从 12.7% 压到 1.7%。现在如果 AND 直接用 0.50，相当于把"被拒 3.3%"又加回去（100% − 92.67% ≈ 7.3% 的单次拒绝，含两模型各自漏杀）。**等于用 P3 的成果去换一个 SFace 并不需要的严苛。**

退一步说，SFace 在 0.46 上 FAR 已经是 0/1500，比 0.50 一分钱安全性都没少 —— 0.50 挡住的东西，0.46 全挡住了。

单个模型的定位：

| 模型 | EER | EER 阈值 | @现行线 TAR | @现行线 FAR |
|---|---|---|---|---|
| ArcFace w600k_r50 | 1.87% | 0.069 | 97.87%（@0.30） | 0/1500 |
| SFace 2021dec | 2.00% | 0.218 | 92.67%（@0.50） | 0/1500 |

SFace 的 EER 更高、等 TAR 下 FAR 也更高（要让 TAR 到 97.9% 得把阈值降到 0.30，那时 FAR 飙到 **1.47%**）。**这就是"SFace 比 ArcFace 宽松"的量化表述**，也是为什么它能补撞脸、但不能当主力。

## 四、撞脸侧：阈值不能低于 0.40

19 张素材，按线上口径（每人 3 张模板取 max）：

| SFace 阈值 | A 本人（应放行） | B1 撞脸 李治廷→王力宏 | B2 撞脸 蒲巴甲→王力宏 | C 双胞胎 |
|---|---|---|---|---|
| 0.36 | 2/2 | 1/2 | 1/2 | 3/3 |
| **0.40** | **2/2** | **0/2** | **0/2** | 3/3 |
| 0.46 | 2/2 | 0/2 | 0/2 | 3/3 |
| 0.50 | 2/2 | 0/2 | 0/2 | 3/3 |
| 0.66 | 2/2 | 0/2 | 0/2 | 3/3 |
| 0.68 | **0/2** | — | — | 2/3 |

- **下限 0.40**：低于它，两组撞脸各有 1 个探针能过。
- **上限 0.66**：高到 0.68 时本人开始被误杀（王力宏跨年龄 SFace 最低 0.6603）。
- 双胞胎全程 3/3 —— 再次印证阶段 1：**阈值对同卵双胞胎无效**，AND 也不是它的解。

可行区间 **[0.40, 0.66]**，下四分位 = **0.46**。

## 五、结论

两条相互独立的路走到同一个数：

```
LFW 上限：SFace ≥ 0.451 才能在 1500 个负样本对上零误识
撞脸下限：SFace ≥ 0.40  才能让两组撞脸全挡
交集：[0.451, 0.66]

硬负例侧给出的建议（区间下四分位）→ 0.46
两者重合 → 定 0.46
```

| | 取值 | 理由 |
|---|---|---|
| **FaceId 的 SFace 通过线** | **0.46** | 零误识边界向上取整；撞脸余量 0.06、本人余量 0.20；AND 的 TAR 95.87%（仅比 ArcFace 单独低 2.0pp） |
| 2FA 的 SFace 通过线 | 0.50（不动） | 后面还有口令，可用性不是首要约束；两模块独立配置，本来就该各定各的 |
| ArcFace 通过线 | 0.30（不动） | P3 已定档，本次未涉及 |

**落地时 FaceId 的判定变成：`arc_sim ≥ 0.30` 且 `sface_sim ≥ 0.46`。**

## 六、边界（对外必须照实说）

1. **可测最小非零 FAR = 1/1500 = 6.67e-4。** 本次所有 "FAR 0%" 只能表述为 **"≤ 6.7e-4"**，不能写成"零误识率"。线上 FaceId 的目标比这低两个数量级，本报告给的是**工作点匹配**，不是对 2e-5 的直接测量。
2. **LFW 与真实场景分布不同。** LFW 是野外抓拍、光照姿态各异；FaceId 是用户对着摄像头采集的正面照，类内变异更小、分数更高。所以 LFW 上的 TAR 是**偏保守**的估计。
3. **撞脸侧的样本量很薄**：2 个探针/方向。0.40 这个下限的置信度不如 LFW 侧的上限。落地后应该用真实登录产生的误识样本继续补。
4. **0.44–0.46 三档在本批数据上不可区分**（0.44 与 0.45 的差异只有 1 个负样本）。选 0.46 是因为它正好是零误识边界，不是因为 0.45 更差。
5. 双胞胎与这条线无关 —— 同卵双胞胎在 0.66 之下全部通过，**AND 不是双胞胎的解法**，仍需阶段 3 的歧义拒识。

## 七、GPU 加速（DirectML）：11 倍，且数值等价

LFW 全量 3612 张图在 32 核 CPU 上把约 24 个线程跑满，用了 35 分钟，期间整机交互明显受影响。改用 DirectML 后：

| | 引擎 | 每张（YuNet + ArcFace + SFace） |
|---|---|---|
| CPU | onnxruntime 1.31.0 · `CPUExecutionProvider` | 277.64 ms |
| DirectML | onnxruntime 1.24.4 · `DmlExecutionProvider` | **25.14 ms** |
| | | **11.0×** |

比提速更要紧的是**数值等价** —— 否则 GPU 跑出的分数不能用来支撑本报告的定档：

| 分数数组 | 最大绝对差 | 判据 < 1e-6 |
|---|---|---|
| gen_arc | 2.384e-07 | ✓ |
| gen_sf | 4.172e-07 | ✓ |
| imp_arc | 2.086e-07 | ✓ |
| imp_sf | 7.749e-07 | ✓ |

最大差 7.7e-7，是浮点末位噪声，比任何有意义的阈值差别（0.01 量级）小四个数量级。两轮（CPU / DML）跑出的所有工作点数字 —— 97.87% / 92.67% / 0.451 / 22 个冒名者 —— **逐位相同**。所以本报告的数字与用哪个 EP 跑无关。

环境（独立 venv，不动 `envs/faceid`）：

```bash
<faceid-dml venv>/Scripts/python.exe
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple numpy "opencv-python<5" onnxruntime-directml
```

⚠️ 两个坑：① 本机直连 pypi 会 `ReadTimeoutError`，必须换国内源；② DirectML 要先 `enable_mem_pattern = False`，否则与其分配器不兼容。

GPU 只加速两个识别模型；YuNet 检测走 OpenCV 内置实现，仍在 CPU，但只占那 25 ms 的一小部分。

## 九、落地核对（2026-10-24）

### 9.1 生产管线与标定管线是否同一条

0.46 是在 **Python 参考管线**上标出来的（ARCFACE_DST 五点对齐 → 同一张 112×112 图
喂两条预处理）。如果 C# 引擎的第二条前向与它不一致，线上就是另一条管线，
0.46 只是个数字 —— 而且不会报错，只会表现为"有些人莫名其妙登不进去"。

用 `.workbuddy/tmp/faceid-quant/cs_sface_equiv.py` 逐图对照（C# CLI `--faceid-embed`
与 `--faceid-embed --sface`，各取一次向量；参考侧直接复用本报告脚本的 `embed_both`，
不另抄一份实现）：

| 样本 | 有效张数 | min cos 主模型 | min cos SFace | 判据 ≥0.999 |
|---|---|---|---|---|
| LFW 抽样 | 12 | 0.999999 | 0.999999 | ✓ |
| LFW 抽样 | 60 | 0.999999 | 0.999999 | ✓ |

**结论：两条管线数值等价 ⇒ 本报告的阈值可直接用在生产管线上。**

### 9.2 判定口径（写进 `FaceIdDecision.ClassifyPair`）

| 主模型 | SFace | 结论 | 说明 |
|---|---|---|---|
| Pass | Pass | **Pass** | 两个都要过 |
| Pass | 否决 | **Mismatch（计次）** | AND 的唯一新增拒识来源 |
| GrayZone | 任意 | **GrayZone（不计次）** | 否决**只作用于 Pass** |
| Mismatch | 任意 | **Mismatch** | 与单模型一致 |

两条必须解释清楚的不对称：

1. **灰区只挂在主模型上。** 若让 SFace 的否决也作用于灰区，通过集合一个都没变
   （都没过），却凭空多出一条"把边界上的本人推向锁号"的路径 —— 攻击者没多得
   一个字节，本人却更容易被锁。所以否决只作用于 Pass。
2. **SFace 没有灰区。** 灰区宽度必须由该模型的**本人分布**标出来，而 SFace 侧
   没有做过这项标定；照搬 0.05 会凭空造出一条"试了不锁"的地带，而撞脸样本在
   SFace 上能摸到 0.40 附近（§四），那正是最不该给免费试错机会的区间。
   ⇒ **已知代价**：AND 的 TAR 95.87%，约 4% 的本人会在主模型通过后被 SFace 否决
   并计一次失败。多张模板取 max 已把它摊薄，但要消掉它必须先补 SFace 本人分布的标定。

### 9.3 作用单元

AND 的作用单元是 **"两个模型各自取模板 max 之后相与"**，不是"任一副本两模型都过"。
线上没有逐副本比对这一步（每人 ≤3 张模板，逐张取 max），两种写法在评估上会得到
不同数字。实现按前者，`FaceIdLoginService` 里两轮 `max` 分别累计，再进 `ClassifyPair`。

### 9.4 模板作废与重录

`modelId` 从 `cv:<主模型>:<指纹>:512` 变成
`cv:<主模型>:<指纹>:512+<SFace>:<指纹>:128`，因此**全部历史模板一次性作废**
（状态接口会报 `modelMismatchCount`）。这是刻意的：只记主模型的话，换了 SFace
权重后老模板仍被判"可用"，AND 的一半来自旧特征空间、一半来自新空间。

模板同样从单向量（`cipher`）变成一对（`cipher` + `cipher2`，`version=2`）。
两组的 AAD **不同**（`...|sface` 后缀），否则两组密文互换位置后解密仍然成功。

→ **落地动作：所有已录入账号必须重新录入**（对着摄像头重录，不是数据迁移 ——
旧模板里根本没有 SFace 向量，无法从密文推出）。
