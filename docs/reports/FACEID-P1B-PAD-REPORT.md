# FaceId P1b · 活体判定（PAD）接入与阈值标定 交付报告

> 范围：`AuthServer/Services/FaceId/` 的**被动活体判定**（单帧、无动作提示）与它的阈值标定。
> 不含 CLIP 真人判定（已决定暂不纳入，理由见 §六）。
> 上一阶段：`docs/reports/FACEID-P1-ENROLL-REPORT.md`（录入闸门与模板存储）。

## 一、结论速览

| 项 | 结果 |
|---|---|
| 模型 | MiniFASNetV2，**1.7 MB**，Apache-2.0，`sha256 fa2cddb6…`（可入库、可分发） |
| 形态 | **被动、单帧**：不给动作提示，只看这一帧的纹理线索 |
| C# ↔ Python 等价 | **46/46**，`max\|Δ\| = 9e-7`（判据 `1e-4`） |
| 标定样本 | 活人 **46** 帧（`left-ok`）+ 攻击 **120** 帧（手机 40 / 打印 40 / 回放 40） |
| 分离效果 | 活人 `median 0.968`；三类攻击 `max 0.0030`；**阈值 0.70 下攻击通过 0/120** |
| 活人单帧通过率 | 阈值 0.70 ⇒ **91%**（录入是"任一帧通过即可"，整次录入不会被这一条拒） |
| 探针 | **64/64**（新增活体组：照片被拒 + 计次 + 模型缺失 503 + 关掉对照放行） |
| 单测 | **203/203**（P1a 195 + 新增 8） |
| 阈值 | `PadMinLive = 0.70` **保持不变**（标定数据不支持收得更松，也没有理由收得更紧） |
| **默认状态** | **活体：关闭**（`AUTHBASELINE_FACEID_PAD_ENABLED=true` 开启）· **多脸：拒绝**（`AUTHBASELINE_FACEID_ALLOW_MULTI_FACE=true` 放行） |
| 照片可否录入 | **可以**：120 帧翻拍样本在"活体关闭 + 多脸放行"下 **120/120** 过质量闸门 |

## 二、接入方式

| 文件 | 作用 |
|---|---|
| `Services/FaceId/IFaceIdLiveness.cs` | 接口：`Score(frame, box) → [0,1]?`，`Status` 报就绪/不可用 |
| `Services/FaceId/CvFaceIdLiveness.cs` | 真实实现（OpenCvSharp DNN，`ReadNetFromONNX`） |
| `Services/FaceId/StubFaceIdLiveness.cs` | 假实现，行为由 `AUTHBASELINE_FACEID_STUB_BEHAVIOR` 切换 |
| `Services/FaceId/FaceIdPadCli.cs` | `--faceid-pad` 子命令，导出 `live` 分数供等价性对照 |
| `Services/FaceId/FaceIdCaptureCli.cs` | `--faceid-capture` 子命令，**纯采集、不提示动作**（标定用） |
| `tools/faceid_pad_check.py` | `--compare` 等价性 / `--dist` 阈值标定 |

判定排在**质量闸门之后**：脸太小、侧脸、糊的帧连"是不是人脸"都存疑，拿去问活体模型只会得到噪声；
而且先报"太远/太糊"对用户更有用 —— 那类原因他能自己纠正，"未通过活体检测"他只能莫名其妙。

## 三、预处理红线（改任何一项都不会报错，只会安静地给错分数）

| 项 | 取值 | 依据 |
|---|---|---|
| 裁剪 | 检测框中心扩 **2.7 倍**，夹到画面内 | 上游文件名里的 `2.7` |
| 尺寸 | resize **80×80**，**不做五点对齐** | 模型在原样裁块上训练，对齐反而破坏纹理线索 |
| 通道 | **BGR**，不交换 | 与上游 `cv2.imread` 一致 |
| 数值 | **保持 0–255，绝不除 255** | ⚠️ 见下 |
| 输出 | 3 类 softmax `[print, live, replay]`，取 `p[live]` | 上游训练标签顺序 |

⚠️ **除 255 是最危险的一次"看起来更规范"的改动**：实测把 46 帧真人样本的 `live`
从 0.88 压到 0，全部被判成"屏幕回放" —— 本人永远录不进去，而且**不报任何错**，
只会得到一句"未通过活体检测"。这条红线已写进 `AuthServer/face-models/README.md`。

另一个坑：换模型前必须先跑 `--compare` 验证"分数确实随画面变化"。
我们最初的候选导出（`garciafido` / `deepface` 那份）46 帧之间的概率差 **< 0.001**，
等于对输入几乎不敏感 —— 那是一份坏导出，已弃用。

## 四、标定数据

采样条件：同一台摄像头（640×480）、同一室内光线、`--faceid-capture` 40 帧 / 间隔 150 ms。
活人组复用 2FA 录制留下的 `tools/fixtures/face/left-ok`（同一设备、同一分辨率）。

| 组 | n | min | p5 | median | max | ≥0.30 | ≥0.50 | ≥0.70 | ≥0.80 |
|---|---|---|---|---|---|---|---|---|---|
| 活人 | 46 | 0.0039 | 0.2672 | **0.9681** | 1.0000 | 93% | 93% | **91%** | 89% |
| 手机屏翻拍 | 40 | 0.0000 | 0.0000 | 0.0001 | **0.0030** | 0% | 0% | 0% | 0% |
| 打印照片 | 40 | 0.0000 | 0.0000 | 0.0000 | **0.0002** | 0% | 0% | 0% | 0% |
| 视频回放 | 40 | 0.0000 | 0.0000 | 0.0002 | **0.0023** | 0% | 0% | 0% | 0% |

复现命令：

```bash
<faceid venv>/python tools/faceid_pad_check.py --dist \
  --live tools/fixtures/face/left-ok \
  --spoof tools/fixtures/pad/spoof-phone tools/fixtures/pad/spoof-print tools/fixtures/pad/spoof-replay
```

### 怎么读这张表

- **阈值 0.30 到 0.80，攻击组通过数都是 0/120**。也就是说这套样本里没有"临界样本"，
  阈值在很宽的区间内都能用 —— 这说明模型抓到的不是噪声，而是稳定的纹理差异。
- 活人组的 `min 0.0039` 来自少数废帧（糊 / 侧脸 / 转头中），它们本来就该被拒；
  录入逻辑是"**任一帧通过即可**"，所以影响的是单帧通过率，不是整次录入的成功率。
  这也解释了为什么 0.70 比 0.30 只掉 2 个百分点却更安全。
- 单帧层面 `live_min 0.0039 > spoof_max 0.0030` 只是**两个极值碰巧错开**，
  差值 0.0009 没有任何统计意义，**不构成"完全不重叠"的结论**（样本量不够）。

## 五、口径（不许说满的地方）

1. **样本量小、单设备、单光线、单个被摄者**。120 帧攻击样本来自**一次会话**，
   不能换算成 FAR/FRR 估计值。这里能说的只有："在这套采集条件下，三类翻拍全部被拒"。
2. **用的是公开人物（鲍喜顺）的照片，不是本人照片**。活体模型判的是"这是不是一张真脸在镜头前"，
   与人脸身份无关，所以**阈值标定依然有效**；但**不能用它论证"能/不能冒充本人登录"** ——
   要演示后者，攻击样本必须是账号本人（dio 本人）的照片。
3. **不是 PAD 认证**。没有做过 ISO/IEC 30107-3 的 PAD 测试，没有测过 3D 面具、
   深度伪造视频、高亮屏 + 防窥膜、逆光/强光下的屏幕。**只能说"拦住了这三类低成本翻拍"。**
4. **被动单帧的固有上限**：不做动作挑战 ⇒ 对"预录的本人双向视频"没有额外抵抗。
   这正是 2FA 走动作挑战、而本模块（纯人脸登录）只能靠纹理的原因。
5. **录入侧的 PAD 安全价值有限**：录入本身要求已登录 + 二次口令，攻击者就是账号本人。
   真正需要 PAD 的是 **P2 的登录链路** —— 那里的判定必须复用同一个 `IFaceIdLiveness`，
   否则"录入严、登录松"等于白做。

## 六、用照片做识别测试（本项目实际的验收方式）

本项目的验收要覆盖**不同人种、明星各年龄段、双胞胎、特殊人群**——这些场景找不到真人来配合，
只能拿照片（举着手机对着摄像头，或直接喂图）。所以这里定的是"照片必须能一路走通"：

| 环节 | 默认行为 | 照片测试是否会卡住 | 结论 |
|---|---|---|---|
| 活体判定 | **关闭** | 会（关掉后不参与） | ✅ 默认关；开启方式见下 |
| 多脸拒绝 | 拒绝（取最大那张） | 举手机时操作者自己容易同框 ⇒ **会卡** | ✅ 提供 `ALLOW_MULTI_FACE` 放行 |
| 人脸太小（<12% 画面宽） | 拒绝 | 手机举远会卡 | 举近即可（实测翻拍样本脸宽中位 0.15） |
| 正脸度 / 清晰度 | 拒绝 | 照片是静态正脸，**不会卡** | ✅ 实测 120 帧全部通过 |
| 每人 3 张上限 | 3 | 测多人时要"录一个删一个" | 用 `--faceid-delete` 或界面删除清理 |

实测（`--faceid-capture` 采的 120 帧翻拍，按闸门逐条模拟）：

```
spoof-phone    {'★ 可录入': 40}
spoof-print    {'★ 可录入': 40}
spoof-replay   {'★ 可录入': 40}
```

### 开关

| 目的 | 环境变量（启动前设） | 默认 |
|---|---|---|
| 让照片能录入 | （默认就是关的，无需设） | 活体 关 |
| 临时演示反欺骗 | `AUTHBASELINE_FACEID_PAD_ENABLED=true` | — |
| 允许自己与手机同框 | `AUTHBASELINE_FACEID_ALLOW_MULTI_FACE=true` | 多脸 拒绝 |

两个开关的效果都会写进**启动日志**和**账号页卡片**（`活体判定：已关闭（照片可通过）` /
`多脸画面：已放行（取最大那张）`），不会出现"以为有活体、其实没有"的情况。

### 识别精度的离线评测

界面上一次只能录一张、删一张，测"同一个人不同年龄段"太慢。用 `tools/faceid_similarity_check.py`
直接调后端自己的 `--faceid-embed`（**与线上同一条管线**）算 1:N 余弦：

```bash
<faceid venv>/python tools/faceid_similarity_check.py \
  --template <模板图目录> --probe <探针图目录>
```

实测两组（同一台机器、同一管线）：

| 组 | n | min | 中位 | max | 阈值 0.50 的判定 |
|---|---|---|---|---|---|
| 同一个人（`left-ok` 前 20 张当模板、后 26 张当探针） | 26 | 0.0025 | **0.8601** | 0.9675 | Pass 17 / 灰区 3 / 不匹配 6 |
| 不同人（模板=本人，探针=鲍喜顺翻拍） | 40 | 0.1804 | **0.2076** | 0.2340 | 全部不匹配 |

两组差得很开（0.21 ↔ 0.86），说明"0.50"这个起点在离线图集上是站得住的；
同人组里那 6 张不匹配的帧，是转头/糊掉的废帧（余弦低到 0.0025），不是阈值问题。

⚠️ 双胞胎会落在灰区甚至误通过 —— 这是 ArcFace 类模型的已知边界，**必须如实写进报告**，
不要用"识别准确率 96.83%"去暗示它可以区分同卵双胞胎。

## 七、CLIP 真人判定：暂不纳入

| 理由 | 说明 |
|---|---|
| 覆盖面窄 | YuNet 训练在真人脸上，卡通/动物基本检不出 ⇒ 已经走 `FACEID_NO_FACE` 拒绝 |
| 与 PAD 重叠 | "屏幕上放视频"由 PAD 管；CLIP 只覆盖"画得像真人的假脸"这一个窄场景 |
| 代价大 | 视觉塔 350 MB（fp32）起，安装包 222 MB → 约 570 MB；工期 3–5 小时 |
| 可后补 | 接口位置已经留好，P2 之后按需补，不影响现有链路 |

## 八、待办

- ⚠️ **登录链路（P2）必须再过一次 PAD**，并复用 `FaceIdCodes.IsCounted` 的计次语义。
- **真机端到端验收**：桌面端 → 账号页 → 纯人脸登录 → 录入，确认本人在自己光线/距离下能过
  （探针用的是假引擎，覆盖不了摄像头与真实光线）。
- 样本扩充：换光线（逆光 / 夜间无明显光源）、换设备、加"高亮屏 + 防窥膜"一组。
- 若 P2 上线后仍需更强反欺骗：优先**动作挑战**（复用 2FA 的挑战机制）而不是继续堆模型。
