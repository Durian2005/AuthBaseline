# 一次性口令（哈希链）认证 · 通用验收指南

> 适用对象：想复现或检查本方案的同学。
> 配套的设计说明（讲"为什么这么做"）在项目里的 `docs/design/OTP-HASHCHAIN-DESIGN.md`；本文只讲**怎么验**。
> 结论先行：下面列出的检查项，在当前版本上全部通过（最近一次核对：2026-11-10）。

---

## 一、这套方案在验什么

一句话：登录时**不再传输口令明文**。客户端把口令折叠成一条哈希链上的某一格，服务端只做一次哈希比对，拿到的永远是"某一格"而不是口令本身。

因此验收核心是四件事：

1. **口令不上网** —— 抓请求体看不到口令，连字段都不存在；
2. **一格只用一次** —— 同一格提交第二次必被拒；
3. **链不会用尽** —— 低余量时自动换新链，用户无感；
4. **原有功能不变** —— 人脸、审计、角色权限、二次确认都照常。

## 二、准备工作

| 项 | 建议 |
|---|---|
| 运行环境 | .NET 8 + 本地 MongoDB。**用一个新的库名**，不要指向已有数据 |
| 客户端 | 桌面端（安装包或源码构建）即可；也可以直接用 HTTP 调接口 |
| 账号 | 至少两个：一个正常账号、一个用来试"重建链" |
| 链长 | 默认 1000。验收时建议临时改小（如 100），能更快走到"续期"和"用尽" |
| 观察点 | 客户端界面 + 数据库里的链记录（用 Compass 之类点开看，不必敲命令） |

把链长改小的方式：启动后端前设置环境变量 `AUTHBASELINE_OTP_LENGTH=100`。
这个值只决定"缓冲有多深"，不改变任何判定结论。

## 三、照着做：六步

| # | 操作 | 应该看到 |
|---|---|---|
| 1 | 用正确口令登录 | 登录成功，界面与改造前无差别；数据库中该账号的链记录里，`k` 减 1、`v` 变成新值，其余字段不变 |
| 2 | 看请求体（浏览器/代理抓包均可） | 只有 `username`、一格链值、一个一次性挑战凭据；**没有 `password` 字段** |
| 3 | 把上一步成功的那一格再提交一次 | 被拒，且 `k` 不变（失败的尝试不消耗配额） |
| 4 | 改密码，然后用**旧口令**登录 | 失败；用**新口令**登录成功，链记录里的种子换新、代数 +1、`k` 回到满值 |
| 5 | 做一次敏感操作（新建账号 / 删除人脸） | 要求当场再认证一次；通过后操作执行，请求体里依然没有口令 |
| 6 | 打开审计页 | 能看到本次登录成功、链核销、以及第 3 步那次失败被记录；失败原因与实际原因一致 |

第 4 步是整套方案最容易出问题的地方：**口令一改，旧链就绑在一个没人知道的口令上**，
所以改密必须同时重建链。如果改密后新口令登不进来，说明重建没生效。

## 四、通过标准

| 检查 | 通过的表现 | 不通过意味着 |
|---|---|---|
| 口令不上网 | 登录请求里根本没有口令字段 | 客户端仍在传明文 |
| 一次性 | 同一格第二次提交被拒 | 核销没有真正推进 |
| 严格相邻 | 提交相邻的格（上一格或下一格）都被拒 | 存在跳号容忍，重放窗口被放大 |
| 用尽可感知 | `k` 走到 0 时得到"链已用尽、需重建"的提示，而不是"口令错误" | 用户会被误导去反复试口令 |
| 改密换链 | 新口令可用、旧口令算出的格失效 | 链没有跟着口令走 |
| 续期无感 | `k` 到 5% 时登录照常成功，代数 +1、`k` 回满 | 续期失败会连带登录失败 |
| 原有功能 | 人脸、审计、角色、批量操作全部照旧 | 改造引入了回归 |
| 审计可查 | 成功与失败都能查到，且对外话术统一 | 失败原因外泄，可被用来枚举账号 |

其中"口径一致"这条容易被忽略：**对外永远只说"用户名或密码错误"**，
真实原因只写进审计。否则这个接口就成了账号是否存在、账号有没有链的探针。

## 五、必须提前知道的边界

验收时主动说明边界，比被问住更可信：

- **不防实时中继钓鱼**：能挡的是"历史值被重放"，挡不住"你此刻正在被中间人转发"。
- **拿到口令的人当然能冒充**：本方案的收益是"**数据库被拿走 ≠ 可冒用**"，不是"口令泄露也安全"。
- **"一次性"是有配额的**：配额靠静默续期维持；配额存在的意义是限制历史值的可重放窗口。
- **抗离线爆破依赖口令派生函数**：如果把 PBKDF2 换成裸哈希，拖库场景下反而比传统口令存储更差。
- **挑战签名是纵深防御**：TLS 开启时完整性已由传输层保证；它真正发挥作用的是明文传输的场景。
- **同一台机器的其他进程**：本机的配对密钥能挡住其他 Windows 用户，挡不住同一用户下的进程 —— 这是本机威胁模型的固有边界。

## 六、常见现象怎么解释

| 现象 | 原因 |
|---|---|
| 登录报"用户名或密码错误"，但口令没错 | 挑战凭据默认 120 秒过期，重开登录页即可；这**不计**登录失败次数 |
| `k` 变成 0 后完全登不进来 | 链已用尽。客户端会本地拦住、不再发请求；需要管理员为该账号重建链（用服务的重建子命令，需提供当前口令，或显式确认强制重置） |
| 服务起来了但所有接口 500，响应体为空 | 数据库结构与程序版本不匹配（常见于连了旧库）。换一个新库名重试 |
| 换了一台机器就登不进来 | 不会发生：客户端不保存任何秘密，秘密只有口令；链的进度由服务端下发 |

---

## 七、结论

上述六步在本项目当前版本上全部通过：口令不出现在协议里，一格只用一次，改密即换链，
续期对用户不可见，人脸与审计等既有功能无回归。
