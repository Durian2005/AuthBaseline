# OTP 功能验收清单

> 配套设计：`docs/design/OTP-HASHCHAIN-DESIGN.md`（v3）
> 用途：每次改动 OTP 相关代码后，按本清单做一次功能验收。
> 约定：**除特别标注外，所有涉及写库的检查都在探针库执行**，真实库不参与。

---

## 零、前置条件

| 项 | 要求 |
|---|---|
| 后端 | 可启动，日志中打印出 OTP 档位（开关 / 链长 / 迭代次数） |
| 数据库 | 使用库名含 `Probe` 的实例；生产库不连接 |
| 账号 | 至少两个：一个已迁链、一个仍是旧路径（用于验证迁移分流） |
| 配置 | 手工验收阶段可临时调小 `N`（如 100）以便覆盖续期路径 |

## A. 登录路径

| ID | 操作 | 期望 |
|---|---|---|
| OTP-01 | 正常账号输入正确口令登录 | 登录成功，响应含票据；界面与改造前无差别 |
| OTP-02 | 输入错误口令 | 失败，话术与改造前一致（不区分「用户不存在」与「口令错误」） |
| OTP-03 | 未知用户名调用 `login/challenge` | 返回格式合法的随机 `R`/`k`/`N`，与正常响应**逐字一致** |
| OTP-04 | 用上一步拿到的参数登录 | 失败，话术与 OTP-02 相同 |
| OTP-05 | 检查登录响应体 | 不包含除 `R`、`k` 之外的任何链内部值 |

## B. 链状态

| ID | 操作 | 期望 |
|---|---|---|
| OTP-06 | 登录前后对比 `OtpChains` | `v` 变化，`k` 减 1，其余字段不变 |
| OTP-07 | 登录前后对比 `Users` | `passwordHash` 为空且不再写入；`lastLoginAt` 更新 |
| OTP-08 | 提交上一次成功的链值 | 拒绝，且 `k` 未变化 |
| OTP-09 | 提交 `x_{k-1}` 或 `x_{k+1}` | 拒绝（严格相邻，不做跳号容忍） |
| OTP-10 | `k = 1` 时登录 | 成功，随后 `k = 0`；再次尝试返回「需重建」而非「凭据错误」 |
| OTP-11 | 两个请求并发提交同一格 | 恰好一个成功，另一个按失败处理，`k` 只减 1 |

## C. 续期

| ID | 操作 | 期望 |
|---|---|---|
| OTP-12 | 使 `k` 降到 `N × 5%` 后登录 | `generation` +1，`k` 回到 `N−1`，`r` 变为新值 |
| OTP-13 | 续期后立即用旧链的下一格登录 | 拒绝（旧链已失效，不存在并行窗口） |
| OTP-14 | 注入登记新链的写失败，再登录 | **本次登录仍成功**，`k` 按旧链继续递减，日志出现续期失败记录 |
| OTP-15 | 使 `k` 跌破 `N × 1%` | 日志出现警戒告警 |

## D. 二次确认

| ID | 操作 | 期望 |
|---|---|---|
| OTP-16 | 删除人脸 | 要求链值再认证，通过后执行；界面无额外输入框 |
| OTP-17 | 再认证时提交错误值 | 拒绝，且 `FailedLoginAttempts` **不变** |
| OTP-18 | 用同一张确认凭据重复调用敏感接口 | 第二次拒绝（一次性） |
| OTP-19 | 创建账号 / 角色任免 | 同 OTP-16 |
| OTP-28 | 拿「录入人脸」的确认去删人脸 | 拒绝，**且该凭据当场作废**（不能换个端点再试） |
| OTP-29 | 拿「给 A 的确认」去操作 B | 拒绝（凭据绑定目标账号） |
| OTP-30 | 确认凭据超过 TTL 后使用 | 拒绝并提示重新确认；**签发本身不消耗链** |
| OTP-31 | 连续 5 次错误链值后的第 6 次 | 429 `OTP_RECONFIRM_THROTTLED`；`FailedLoginAttempts` 仍为 0、登录不受影响 |

## E. 迁移

| ID | 操作 | 期望 |
|---|---|---|
| OTP-20 | 旧路径账号首次登录 | 验证通过后自动建链，`passwordHash` 暂保留（回滚用），审计出现 `OTP_MIGRATED` |
| OTP-21 | 同一账号第二次登录 | 不重复建链、不重复写 `OTP_MIGRATED`。**P7（客户端计算）之前仍走口令路径**；P7 之后走链值路径 |
| OTP-22 | 手工清空 `passwordHash` 后登录 | 仍成功（纯链路径可用）。**P8 才允许清空**，P3 阶段必须保留以便回滚 |

## F. 异常与边界

| ID | 操作 | 期望 |
|---|---|---|
| OTP-23 | 关闭 OTP 总开关后登录 | 回退旧路径，与改造前一致；日志说明当前档位 |
| OTP-24 | `OtpChains` 索引创建失败 | 服务仍能启动，日志报出降级 |
| OTP-25 | 注销账号 | `OtpChains` 记录被真删，无孤儿数据 |
| OTP-26 | 口令含非 ASCII 字符 | 按 UTF-8 编码参与派生（**不做 Unicode 归一化**，客户端须一致）；同一口令在不同客户端结果一致 |
| OTP-27 | 改密 | 旧凭据（口令或链值）+ 新口令；成功后链重建，**旧链所有格立即失效**（OTP-32） |

## I. 客户端（P7 起）

这一节验的是"客户端真的算出来了"，而不是"服务端接受这种请求"。
判据刻意不取界面文案 —— 界面正常但功能从未生效，是这个模块最可能的失败形态。

| ID | 操作 | 期望 |
|---|---|---|
| OTP-39 | 新装机器上首次登录 | 走**口令**路径（本地还不知道有没有链），登录后学到"有链" |
| OTP-40 | 第二次登录（提示已在） | 走**链值**路径；服务端审计出现 `OTP_CONSUME` / `OTP_CHAIN_VERIFIED`（这是"客户端真的算了一格"唯一的硬证据） |
| OTP-41 | 登录耗时对比 | 链值路径 **不慢于**口令路径（客户端多付 PBKDF2，服务端省掉 BCrypt）；增量 < 200 ms |
| OTP-42 | 建号（六处二次确认之一） | 请求体里**没有口令字段**，只有 `confirmToken`；服务端审计 `OTP_RECONFIRM_OK` 带正确的用途与目标 |
| OTP-43 | 关掉 `Otp:Enabled` 后重登 | 挑战端点 404 `OTP_DISABLED`，客户端退回口令路径，界面表现与改造前一致 |
| OTP-44 | 桌面壳里 `invoke('otp_compute')` | 返回 `{ code, nextR, nextHead, elapsedMs }`；被 ACL 拒绝时控制台必须出现 `[otp] 本地计算不可用` |

| OTP-44 IPC 返回形状 | ✅ 自动 | `otp_p7_ui_e2e.mjs` E6（背后是 Rust 单测 6 项固定向量） |

另有两条只在探针里成立、清单里没有的断言，值得单独记一笔：

- **跨实现向量一致**：探针用 Python 的 `hashlib` 独立算出 `x_k`，服务端接受它 ——
  这证明 C# 侧的 PBKDF2 加盐方式、UTF-8 编码与 SHA-256 迭代方向都能被第三方实现复现，
  也是将来 Rust 客户端能不能对上的提前验证。
- **旧路径在链存在前后逐字不变**：A1/A2 与 A4/A5 分别在"库里有链"之前与之后各跑一次，
  话术、状态码、计数全部一致。

## K. 挑战签名（防小数攻击，2026-11-10）

验收方式：`tools/otp_challenge_proof_probe.py`（10 项，端到端跑真实后端）
+ xUnit `OtpChallengeKeyTests`（8 项）+ Rust `otp::tests` 的 3 条签名用例。
两侧断言的**是同一组固定向量**（期望值由 Python 独立算出），因此"跨实现一致"是被钉住的，不是推测。

| # | 断言 | 结果 | 证据 |
|---|---|---|---|
| OTP-55 挑战带签名 | ✅ 自动 | `login/challenge` 返回 `proof`；probe A1 |
| OTP-56 跨实现一致 | ✅ 自动 | probe A2（Python 用同一份 DPAPI 密钥复算，与服务端逐字相同）；同一向量在 C# 与 Rust 各断言一次 |
| OTP-57 篡改 `k` 即失效 | ✅ 自动 | probe A3；Rust `tampered_k_breaks_signature` |
| OTP-58 篡改 `R` / `N` / 用户名即失效 | ✅ 自动 | probe A4/A5；xUnit `Sign_CoversEverySignedField` |
