# 僵尸账号治理设计

> **状态：已定稿，按本文实施。**
> 本文讲"要做什么、为什么这么做、边界在哪"。实现细节见代码与 `tools/` 下的探针。

---

## 一、先厘清概念：什么叫"僵尸账号"

业界没有统一定义，但可归成**四类**，处理方式差别很大。混为一谈是这类功能最常见的失败原因：

| 类型 | 特征 | 典型判据 | 处理强度 |
|---|---|---|---|
| **A · 沉睡账号**（dormant） | 真实用户注册过，但长期不用 | 最后一次成功登录距今 > N 天 | 温和：提醒 → 冻结（可自助恢复） |
| **B · 废弃账号**（abandoned） | 长期不用 **且** 无任何业务痕迹 | 最后一活动距今 > N **且** 名下无数据 | 较强：注销或匿名化 |
| **C · 孤儿账号**（orphan） | 账号对应的责任人已离开 | 组织架构 / HR 状态变更，非登录时间 | 即时：随人走 |
| **D · 机器账号**（service） | 供程序调用，本就不"登录" | 账号类型标记 | **永不**按登录时间治理 |

⚠️ **本项目最容易踩的坑**：`admin` 等管理账号可能很久不登录，但它**不是僵尸** —— 它是系统得以运转的前提。判断标准里必须有一条"角色豁免"。

## 二、成熟软件的通行做法（六个维度）

### 2.1 判定标准：用什么信号判断

| 方案 | 判据 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| **登录时间**（最常用） | `lastLoginAt` 距今 > N 天 | 简单、直观、易解释 | 只看"来没来"，看不出"用没用" | 绝大多数 B2C / 内网系统 |
| **任意活动时间** | 登录 + 改密 + 业务操作取最大 | 更准确 | 需要埋点覆盖全部写操作 | 有丰富业务行为的系统 |
| **注册后从未登录** | `lastLoginAt == null` 且创建 > N 天 | 精准识别"注册即弃" | 只管一类 | 拉新质量分析 |
| **复合判据** | 时间 + 无数据 + 非关键角色 | 最贴近"真正可清理" | 规则复杂 | 做**注销**前的收紧判据 |
| **行为风险** | 异地、异常时段等 | 面向安全 | 与"沉睡"是两回事，别混用 | 风控系统 |

**通行阈值**（供参照，非金科玉律）：消费级 90/180/365 天分档；企业内网多为 90 天；受监管行业不自动注销，只"停用"。

### 2.2 检测周期：什么时候跑

**通行做法**：**每日一次低峰批量扫描**，输出"候选清单"但不直接处置。这样扫描是幂等的、可重放的，出错也不会造成不可逆后果。

| 方案 | 优点 | 缺点 |
|---|---|---|
| **定时批量**（每日 / 每周） | 实现简单、结果可预期、便于留痕 | 不是实时；集中扫描对库有一次负载 |
| **登录时惰性触发** | 零额外扫描 | 覆盖不到"再也不登录"的账号 —— 而这类恰恰是目标 |
| **事件驱动 + 定时兜底** | 兼顾 | 复杂度最高 |

### 2.3 状态标记：怎么表示

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **加状态枚举** | `Status` 增加 `Dormant` / `Suspended` 一类值 | 语义清晰，鉴权只需看一个字段 | 要改状态机与所有判定分支 |
| **加时间戳字段** | `lastLoginAt` / `dormantSince` | 不动状态机，向后兼容好 | 判定逻辑散落，容易漏改 |
| **不标记，纯扫描** | 每次现算 | 零改动 | 无法承载"通知了几次""何时该删" |

⚠️ **关键设计点**：无论走哪条，"**检测**"与"**实际失效**"必须分离 —— 标记成"沉睡"时账号通常**仍能登录**（登录即自动复活），真正不能登录的是"冻结"。把两者合并会让"误判"直接变成"用户进不来"。

### 2.4 通知策略：怎么告知

**通行做法是"递进通知"**：T-30 天提醒 → T-7 天再提醒 → 处置前一天最后提醒。每次通知都记进审计。

⚠️ **本项目的现实约束**：管理类账号（`Admin` / `UserAdmin` / `AuditAdmin`）**一律不绑邮箱**（既有设计）。所以对它们**邮件通知不可用**，只能靠管理端显示 + 人工确认。

### 2.5 清理策略：到什么程度

按**可逆性**从轻到重排，**逐级使用，而不是一步到位**：

| 级别 | 动作 | 可逆性 | 代价 |
|---|---|---|---|
| L0 | 仅标记 + 展示 | 完全可逆 | 无 |
| L1 | 标记为沉睡，登录即自动复活 | 完全可逆 | 无 |
| L2 | **冻结**（登录被拒，但可解冻） | 可逆 | 用户被挡在门外，需有解冻通道 |
| L3 | 匿名化（保留账号壳，抹掉身份信息） | 部分可逆 | 破坏可追溯性 |
| L4 | 硬删除 | **不可逆** | 审计断链、合规风险 |

**成熟软件的共识**：默认做到 **L2（冻结）**，L4 只在"确认无人需要"时做且必须单独授权。

### 2.6 数据保留与恢复机制

| 关注点 | 通行做法 |
|---|---|
| 保留期 | 先冻结观察 N 天，确认无申诉再考虑删除 |
| 数据最小化 | 删除前先匿名化用户标识 |
| 可恢复窗口 | 删除前导入归档集合，保留原始文档 |
| 审计完整性 | **绝不删除审计日志** —— 会破坏哈希链 |
| 争议处理 | 冻结 → 申诉 → 恢复 的通道必须存在，且恢复动作留痕 |

## 三、结合本项目的实际情况

### 3.1 现状核查（已逐项确认）

| 项 | 事实 | 对方案的含义 |
|---|---|---|
| **`User` 模型** | **没有 `lastLoginAt` 字段**，只有 `createdAt` | ⚠️ **核心约束**：必须先补字段 |
| **登录审计** | `LOGIN_SUCCESS` **已记录**（`operatorName` + `timestamp`） | ✅ 存量可回填，不必等上线才攒 |
| **审计存储** | 分片 `AuditLogs_yyyyMM`（现有 `202609` / `202610`）+ 哈希链 | ⚠️ 回填要**跨分片查**，且**不得写审计分片** |
| **用户状态** | `Pending` / `Enabled` / `Locked` / `Disabled` | ⚠️ `Disabled` 已在**登录路径被检查**（直接拒），但**原无接口能置成 `Disabled`** ⇒ "半成品"，正好给冻结复用 |
| **角色模型** | 4 角色互斥，职责分离 | 治理必须**按角色分档**，管理账号需豁免 |
| **权限判定** | `UserRoles.CanBeManagedBy(actor, target)` 是唯一出口（含自我豁免） | ✅ 治理动作复用它，不另起第二套规则 |
| **管理账号邮箱** | 一律不绑邮箱 | ⚠️ **邮件通知对管理账号不可用** |
| **真实库现状** | 6 个账号全部 `Enabled`；管理类 4 个、普通 2 个 | ⚠️ 不能"一刀切按时间清理"，且**当前无存量可清** |

### 3.2 本项目的三条特别约束

1. **数据不够用**：`lastLoginAt` 缺失 ⇒ 第一步必须是"补字段 + 回填"。
2. **账号少且角色重**：4/6 是管理类，按时间清理收益极低风险极高 —— 本功能的真正价值是**"可治理的能力"**。
3. **审计不可破坏**：治理动作都要留痕，且**绝不能删审计日志**。

## 四、定稿方案

### 4.1 处理目标（红线）

> **绝不删除任何账号。**
> 建立"可识别 → 可展示 → 可冻结 → 可解冻"的沉睡账号治理闭环。
> 冻结后账号**无法登录**，但可由用户管理员/管理员**一键解冻**恢复。

**明确不做**

- ❌ 删除账号（任何形式，含匿名化、含归档后删除）
- ❌ 自动冻结（冻结必须由人点击）
- ❌ 对管理类账号执行冻结

### 4.2 判定标准

**单一阈值：90 天**（配置项 `Dormant:DormantDays`，不硬编码）。

| 项 | 规则 |
|---|---|
| **基准时间** | `User.lastLoginAt`；为空时回退 `CreatedAt` |
| **判定** | `now - 基准时间 > 90 天` ⇒ 沉睡 |
| **时间源** | `TimeGuard.WallNow()` —— **刻意**复用带演示偏移的墙钟，使"改系统时间/设 `AUTH_TIME_SKEW_SECONDS`"都能推动判定，便于演示 |
| **角色分档** | `User` 类参与判定；`Admin`/`UserAdmin`/`AuditAdmin` **单独分区展示，标注"管理账号 · 不参与冻结"**，永不进冻结候选 |
| **状态前置** | `Pending` 不参与（还没通过审核）；`Disabled`（已冻结）单独列出但**不重复计为沉睡** |
| **自我豁免** | 操作者自己的账号恒不在候选内（复用 `CanBeManagedBy`） |

### 4.3 触发条件

| 触发 | 动作 |
|---|---|
| **管理端查询沉睡清单** | 现算分档 → 返回候选（**只读**，不写任何字段、不写审计） |
| **管理员点击"冻结"** | 置 `Disabled` + 吊销全部票据 + 写审计 `DORMANT_FREEZE` |
| **管理员点击"解除冻结"** | 置 `Enabled` + 写审计 `DORMANT_RESTORE` |
| **登录成功时** | 写 `lastLoginAt`（副作用：自动"复活"，因为基准时间被推到现在） |
| **不做的事** | 查询清单本身不触发任何冻结 |

⚠️ **幂等**：查询清单是纯只读派生计算，**不写审计**，因此不存在刷屏风险。

### 4.4 处理流程

```
① 查询      管理员打开用户管理页 → 拉沉睡清单（90 天阈值，现算，只读）
                                        ↓
② 展示      普通用户分区（可冻结）/ 管理账号分区（只提示"不参与冻结"）
            显示"上次登录：N 天前"或"从未登录"
                                        ↓
③ 冻结      管理员对**单个**普通用户点击冻结 → 二次确认 → 置 Disabled + 吊销票据 + 审计
                                        ↓
④ 解除      被冻结账号持有效理由 → 管理员点击"解除冻结" → 置 Enabled + 审计
            （管理员可随时解除；这是"申请—审批"的可执行形式）
```

### 4.5 涉及模块

| 层 | 模块 | 改动性质 |
|---|---|---|
| 模型 | `Models/User.cs` | **加字段**：`lastLoginAt`（都 `BsonIgnoreIfNull`，老数据兼容）；`UserResponse` 追加 `lastLoginAt` / `dormantDays` / `dormant` / `frozen` |
| 服务 | `Services/DormantAccountService.cs` | **新增**：纯函数分档判定（便于单测）+ 阈值从配置读 |
| 服务 | `Services/MongoDbService.cs` | 启动时**回填** `lastLoginAt`（跨审计分片取最近 `LOGIN_SUCCESS`，只写 `Users`） |
| 控制器 | `AuthController.cs` | 登录成功处补写 `lastLoginAt`；新增 `GET dormant-users` / `POST freeze-user`；扩展 `unlock` 支持 `Disabled → Enabled` |
| 审计 | `Models/AuditLog.cs` | **新增 action**：`DORMANT_FREEZE` / `DORMANT_RESTORE`；**新增 reason**：`NOT_FROZEN` / `DORMANT_PROTECTED_ROLE` |
| 前端 | `UsersView.vue` + `session.js` + `client.js` | 沉睡分区展示；冻结/解除按钮 + 二次确认 |
| 配置 | `appsettings.json` | 新增 `Dormant` 节 |

### 4.6 风险控制

| 风险 | 后果 | 控制措施 |
|---|---|---|
| **误判活跃用户** | 正常用户被冻结 | ① 阈值 90 天偏保守 ② 查询只标不处置 ③ 冻结需人工二次确认 ④ 解冻是一键操作 ⑤ 登录即自动复活 |
| **管理账号被冻结** | 权力真空 | ① 管理角色**结构性排除**在冻结之外（前端隐藏按钮 + 后端拒绝 `DORMANT_PROTECTED_ROLE`）② 复用自我豁免 |
| **破坏审计链** | 治理动作本身成篡改 | ① 绝不删审计日志 ② 全部走 `AuditService.WriteAsync` ③ 查询清单不写审计（天然幂等）④ 完成后跑 `verify_chain_independent.py` |
| **回填改写历史** | 审计分片被污染 | 回填**只写 `Users`**，绝不改 `AuditLogs_*`（只读查询） |
| **数据库负载** | 集中扫描卡库 | 只读一次全表 + 一次跨分片取近期 LOGIN_SUCCESS；6 个账号量级可忽略 |
| **通知发不出去** | 用户不知情 | 界面明示管理账号"无邮箱、需人工确认"；本项目规模下通知识别为"管理端可见" |
| **影响既有功能** | 打破既有回归 | 新增字段全 `BsonIgnoreIfNull`；`UserResponse` 仅**追加**；改完跑全套回归探针（79+25+27+45 项） |

### 4.7 分期

| 期 | 内容 | 状态 |
|---|---|---|
| **P0** | 加 `lastLoginAt` + 登录时写入 + 启动回填 | 本次实施 |
| **P1** | 判定服务 + 沉睡清单接口 + 管理端分区展示（只读） | 本次实施 |
| **P2** | 冻结 + 解除冻结（含二次确认与审计） | 本次实施 |
| **不做** | 删除 / 自动冻结 / 管理账号冻结 | — |

## 五、演示口径

1. **阈值可配**：`appsettings.json` 的 `Dormant:DormantDays`（默认 90）。
2. **演示怎么触发**：把阈值临时改成 `1`（**不是 0** —— 非正数会被后端拒绝并回落 90，防止"阈值误配成 0 而一次冻结所有人"），重启后端；或用探针把某账号的 `lastLoginAt` 改到 100 天前。
3. **改系统时间也能推动**：判定走 `TimeGuard.WallNow()`，把本机时间往后拨即"未登录天数"变大（时间偏移即时生效；阈值改动需重启）。
4. **演示主线**：登录 → 用户管理 → 看到"沉睡账号"分区并显示"上次登录 N 天前" → 冻结 → 该账号登录被拒（`ACCOUNT_DISABLED`）→ 解除冻结 → 恢复登录。
5. **留痕证据**：审计页筛 `DORMANT_FREEZE` / `DORMANT_RESTORE` 两条记录，说明治理动作可追责。
