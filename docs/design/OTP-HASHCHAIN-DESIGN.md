# 一次性口令（哈希链）认证方案

> 版本：**v3（替代式认证）**
> 定位：用哈希链一次性口令**取代**口令存储与验证，而非叠加第二因子。
> 原则：**用户侧无感**——登录仍是一次输入、一次点击。
> 本文只描述设计与边界，不含实现代码。

## 修订记录

| 版本 | 改动 |
|---|---|
| v1 | 初稿：以哈希链作为**第二因子**，独立秘密 `S_otp` |
| v2 | 改为静默续链；链长回退到 1000；修复若干参数错误 |
| **v3** | **改为替代式认证**：`x₀` 由用户口令派生，服务端不再保存任何口令派生物。删除「第二因子」「独立秘密」「DPAPI 保管」等全套内容 |

v1/v2 中与定位无关的结论（静默续链、严格相邻、链状态独立集合、两步写 fail-safe）在 v3 中**继续成立**，已并入下文。

## 一、目标与范围

### 1.1 要做的

1. 以哈希链一次性口令承担**唯一的认证因子**：用户记一个口令，每次登录提交链值。
2. 服务端不保存口令，也不保存口令的任何派生物，只保存链头 `v` 与下标 `k`。
3. 链永不在用户可见层面耗尽：低余量时静默续期。
4. 存量账号**无感迁移**，用户不需要做任何事。

### 1.2 明确不做的

| 不做 | 原因 |
|---|---|
| 把 OTP 叠加成第二因子 | 会让用户持有两个秘密，且与既有的人脸因子语义重叠 |
| 服务端生成或保管用户秘密 | 秘密就是口令，应由用户持有 |
| 跳号容忍（一次推进多格） | 同机部署几乎不丢包，开口子只放大首轮冒用风险 |
| 客户端持久化 `k` | 多设备会不同步；`k` 一律由服务端下发 |
| 任何前台提示、中断、额外操作 | 见 §1.3 |

### 1.3 用户体验不变清单

| 操作 | 变化 | 用户感知 |
|---|---|---|
| 登录 | 仍输「用户名 + 口令」，仍一次点击；链值由客户端计算 | 无（多约 100ms 计算） |
| 登出 / 找回口令 | 不变 | 无 |
| 改密 | 仍输「旧口令 + 新口令」 | 无 |
| 人脸录入 / 人脸登录 | 不变（挂载点未变） | 无 |
| 管理端全部操作 | 不变 | 无 |
| 换设备 / 重装 | **不受影响**——秘密是口令，不在本地文件里 | 无 |

最后一行是替代式认证相对「第二因子」方案的关键优势：客户端**不需要保管任何秘密**，因此没有「本地密钥丢失」这一类故障。

**唯一必须守住的技术前提**：PBKDF2 与 `H^k` 的计算必须在客户端完成且不得触发可感知延迟。放前端 JS 串行算 `H^k` 会卡数百毫秒，应放在 Rust 侧（见 §4.3）。

## 二、认证模型

### 2.1 一句话

用户只记一个口令。客户端把它折叠成一条哈希链上的某一格，每次登录提交**不同的**一格；服务端只做一次哈希比对，从不接触口令本身。

### 2.2 符号与状态

| 符号 | 含义 | 谁持有 |
|---|---|---|
| `PW` | 用户口令 | **仅用户与客户端内存** |
| `R` | 公开链种子（Base32） | 服务端存、可明文下发 |
| `N` | 链长 | 服务端存 |
| `x₀` | `PBKDF2(PW, R)` | 仅客户端内存，**永不提交** |
| `xᵢ` | `H(xᵢ₋₁)` | 客户端按需计算 |
| `v` | 当前验证基准 | 服务端存，**明文** |
| `k` | 期望下标 | 服务端存 |

`v` 不需要加密：它是单向函数的输出，拿到它也推不出 `x_k`。

### 2.3 登录时序

1. 客户端 `POST /api/auth/login/challenge`，带用户名 → 返回 `R`、`k`、`N`、KDF 参数。
2. 客户端本地计算：`x₀ = PBKDF2(PW, R, iter)` → 迭代 `k` 次 `H` 得 `x_k`。
3. 客户端 `POST /api/auth/login`，带 `{ username, code: x_k }`。
4. 服务端取 `v`、`k`，验证 `H(code) == v`，恒定时间比较。
5. 通过 ⇒ CAS 核销（`v = code`、`k -= 1`）⇒ 签发票据。

两次往返，对用户仍是一次点击。

### 2.4 为什么 `Encode` 用 PBKDF2

约定第一步写作 `x₀ = Encode(PW, R)`，其中 `Encode` 取 PBKDF2-HMACSHA256。

理由是 `v` 可被**离线爆破**：攻击者拿到 `v` 与 `R` 后，猜 `PW'` → 算 `x₀'` → 迭代 N 次 → 比对。若 `Encode` 是裸哈希，每次猜测仅约 1ms，比现有 BCrypt 弱两个数量级；换成 PBKDF2 后每次猜测需一次完整的密钥派生，成本回到与 BCrypt 同档。

**这不是可选优化**：若省掉，本方案在「数据库被拖走」这一最重要的场景下会比现状更差。

参数：PBKDF2-HMACSHA256，迭代次数可配置（初值 100 000），输出 32 字节。迭代次数与 `R`、`N`、算法一并记录在链上，便于将来整体升级。

## 三、与现有系统的边界

### 3.1 受影响的路径

现行代码里 `PasswordHasher.Verify` 共 8 处调用，全部需要替换：

| 位置 | 用途 | 替代方式 |
|---|---|---|
| `AuthController:224` | 登录 | 链值验证 |
| `AccountController:500` | 改密验旧口令 | 链值验证（并重建链） |
| `AccountController:617` | 人脸录入确认 | 链值再认证 |
| `AccountController:780` | 人脸删除确认 | 链值再认证 |
| `FaceIdController:132` | 纯人脸录入确认 | 链值再认证 |
| `FaceIdController:252` | 纯人脸删除确认 | 链值再认证 |
| `UserAdminController:609` | 创建账号二次确认 | 链值再认证 |
| `UserAdminController:748` | 角色任免二次确认 | 链值再认证 |

`reset-password` 不受影响：它走邮箱验证码，本来就不验口令。

### 3.2 不受影响的

| 功能 | 说明 |
|---|---|
| 人脸 2FA | **挂载点未变**——它挂在「第一因子通过之后」，第一因子从「验口令」换成「验链值」，逻辑结构一致 |
| 纯人脸登录 | 独立模块，不经过口令路径 |
| 审计哈希链 | 只加原因码，细节进 `request`/`response` 袋，不加列 |
| 会话票据 | 只在认证完全通过后签发 |
| 角色与权限 | 不涉及 |
| 传输层 / TLS | 不涉及 |
| 沉睡治理 | 只依赖 `lastLoginAt`，仍在认证通过处更新 |

### 3.3 一个必须区分的情形

**服务端「知道」口令的时刻**与「保存」口令是两件事。

注册、管理员创建账号（初始口令固定）、`SeedAdmin`（`Admin123`）这三条路径，口令本来就是请求体里的明文。这些场景下服务端可以**当场算出整条链**并只保存链头，口令用完即弃。

这不违背原则——原则是「不保存」，不是「不接触」。

### 4.3 客户端

| 职责 | 说明 |
|---|---|
| PBKDF2 + `H^k` | 放在 Rust 侧。PBKDF2 约 50–100ms，`H^k` 约 1–3ms（k 最大 999） |
| 不持久化任何秘密 | 口令只存在于内存，用完即丢 |
| 不持久化 `k` | 每次从 challenge 取，避免多设备不同步 |

若为减少 Rust 依赖，可让 Web Crypto 承担 PBKDF2（原生实现，性能足够），把得到的 `x₀` 交给 Rust 迭代 `H^k`——两者都在客户端进程内，不构成泄露。

### 5.1 `OtpChains`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | |
| `userId` | string | **唯一索引** |
| `username` | string | 冗余，供注销时按用户名清理 |
| `r` | string | 公开链种子（Base32） |
| `algorithm` | string | `SHA256` |
| `kdf` | string | `PBKDF2-HMACSHA256` |
| `kdfIterations` | int | 与链绑定，便于整体升级 |
| `length` | int | 链长 N（默认 1000） |
| `v` | string | 当前验证基准（Base64），明文 |
| `k` | int | 期望下标 |
| `generation` | int | 第几代链，续期时 +1 |
| `createdAt` | DateTime | |

不存在任何口令或其派生物。

### 5.2 为什么独立集合

`Users` 集合被大量整篇 `ReplaceOneAsync` 覆盖（登录成功、失败计数、解锁、冻结、角色变更）。链状态挂上去后，任何一次覆盖都可能把 `k` 写回请求开头读出的旧值——**静默回滚一格，形成可重放窗口**，且不会报任何错。独立集合后链只由一条 CAS 语句推进。

## 六、接口契约

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/auth/login/challenge` | 匿名 | 返回 `R`、`k`、`N`、KDF 参数 |
| POST | `/api/auth/login` | 匿名 | 提交链值，替换原口令登录 |
| POST | `/api/auth/reconfirm` | 票据 | 链值再认证，换取一次性确认凭据 |
| GET | `/api/auth/otp/status` | 票据 | 剩余格数/百分比、代数、是否该续期。**不下发** `R`/`v` |
| POST | `/api/auth/otp/recover` | 匿名 | 当前口令 + 邮箱验证码 → 重建链（**不改口令**） |

**防枚举（challenge）**：对不存在、已冻结、未建链的账号，必须返回一组**格式合法但随机**的 `R`、`k`、`N`，与正常响应逐字一致。否则该端点就是一个账号枚举接口。随后登录失败统一返回「用户名或密码错误」，审计内部分开记。

**`reconfirm` 的语义**：不签发新票据，只签发一张**短时、绑定操作类型与目标**的一次性确认凭据，供敏感接口消费。这样敏感接口不必各自实现链值比对。

**`status` 为什么不带 `R`/`k`**：它只回答"够不够用、要不要管"，取参仍走 `login/challenge`。
取参路径是防枚举设计里最敏感的一环，多开一条就多一处要验证"是否与挑战端点逐字同形"。

**`recover` 为什么要求两个证明**：只要验证码 ⇒ 拿到邮箱的人能把别人的链换成由他知道的口令派生的那一条；
只要口令 ⇒ 这是一个匿名的口令校验接口，可被无限次试探。两个都要，两个问题一起消失。
顺序固定在**先验证码、后口令**：反过来就是那个匿名试探接口本身。

## 七、链的续期

### 7.1 为什么链不会在用户可见层面耗尽

链只在成功认证时推进。所以：不登录则不消耗；每次登录都是一次续期机会。真正耗尽的前提是「在低余量区连续多次续期失败」，而那只能是服务端持续故障——那种状态下整个系统本就不可用。

### 7.2 机制

`k ≤ N × 5%` 时，客户端在本地生成新链（`R'` 用 CSPRNG，同一口令），随本次登录一并提交 `nextChain: { r, head }`。服务端验证本次链值通过后完成替换。

**窗口外提交的新链一律忽略。** 这一条不是洁癖：若允许随时换链，客户端每登录一次就能把 `k` 刷回 `N-1`，
「链有配额」这件事名存实亡 —— 而配额正是「历史值重放窗口」的唯一约束。判据用的是**核销前**的 `k`，
所以 `k = N×5% + 1` 的那一次登录不会触发续期，紧接着的下一步才触发。

服务端对 `nextChain` 只校验**形状**（`r` 是 32 位 Base32、`head` 是 32 字节 Base64），因为验证内容需要口令。
形状合法但内容错的新链会把账号推进「链不可用」—— 这在 P8 之前是可恢复的（口令路径仍在）。
续期时链长与迭代次数**继承旧链**而不是读当前配置：配置变更不该让同一账号的两代链参数不可比。

链长的含义由此变为**续期失败时的缓冲深度**，而非「可用多久」：

| N | 续期点 | 缓冲 | 客户端 `H^k` |
|---|---|---|---|
| 100 | 95 次后 | 5 次 | < 1ms |
| **1000** | 950 次后 | **50 次** | 1–3ms |
| 10000 | 9500 次后 | 500 次 | 约 15ms |

取 1000：50 次缓冲足以吸收「写库失败」级别的故障，而 N 越大客户端迭代越慢、测试越难覆盖续期路径。

### 7.3 两步写与 fail-safe

**核销本次与登记新链不能放进同一次原子写**，否则续期失败会连带登录失败。

| 步骤 | 必须成功 | 失败后果 | 处理 |
|---|---|---|---|
| a. 核销本次（`k → k-1`） | 是 | 本次登录失败 | 按普通失败处理 |
| b. 登记新链 | **否** | 旧链继续有效 | 忽略错误，本次登录照常成功，下次再试；**写一条日志** |

步骤 b 必须带条件 `r == 当前R`，防止并发下覆盖他处刚换好的新链。

### 7.4 可观测性

对用户静默不等于对系统静默。续期失败必须留下痕迹：当前 `k`、失败原因、链代数。当 `k` 跌破警戒线（如 `N × 1%`）时输出明确告警。否则用户某天登不进来时，系统里没有任何线索能回答「它什么时候开始坏的」。

### 7.5 并发

两个客户端同交一个 `x_k`：步骤 a 用 CAS（`v` 与 `k` 双条件），只有一个成功；失败方按普通失败处理，不可重试成功。

### 7.6 口令变更必须重建链（P6）

链根由口令派生 ⇒ **口令一改，旧链就绑在一个已经没人知道的口令上**。
症状是"口令登录正常、OTP 登录永远失败"；而口令路径是通的，所以没人会觉得系统坏了 ——
直到 P8 移除口令路径才发现这个账号进不来。因此改密/重置/恢复三条路径**都必须重建链**：

| 触发 | 服务端手里有新明文？ | 谁算新链 |
|---|---|---|
| 改密（`change-password`） | 有（`newPassword`） | 服务端，`RebuildAsync`（自己生成新盐） |
| 重置（`reset-password`） | 有（`newPassword`） | 服务端，同上 |
| 恢复（`otp/recover`） | 有（请求里的当前口令） | 服务端，同上 |
| 续期（登录时） | **没有** | 客户端算好递上 `nextChain`（§7.2） |

**重建失败 ⇒ 整个操作失败**（这是本项目唯一"宁可失败也不留半截状态"的地方）：

- 先写 `passwordHash`，再重建链；重建抛错就把口令**回滚**到旧哈希，返回 500 `OTP_REBUILD_FAILED`。
- 反过来（先重建、后写口令）一旦写口令失败，会留下"链绑新口令、口令还是旧的"，
  而用户此时只会去试新口令、得到"口令错"，归因成本高得多。
- 失败计数与锁定状态**不回滚**：它们只会让人更容易进来，回滚反而可能把人锁回去。

**一个已知的边界**：`change-password` 走链值分支时手里没有旧明文，
"新旧口令相同"只能靠 `PasswordHasher.Verify(newPassword, passwordHash)` 判定。
P8 移除 `passwordHash` 之后这条会失效（恒判"没重复"），届时要靠客户端自检 —— 已记入 §9 的清理项。

### 7.7 客户端实现（P7）

**计算放在桌面壳（Rust）里，不在 JS 里。** 三条理由都不是风格问题：

1. **口令用完即擦**：JS 的 `String` 不可变，擦不掉，只能等 GC；Rust 侧用 `Zeroizing` 包住口令与链根，
   函数返回（含 panic）时立刻覆写。
2. **不阻塞渲染线程**：PBKDF2 100k 是纯 CPU 活，放在 IPC 另一侧，登录时界面不会卡一下。
3. **实现只有一份**：盐编码、迭代方向、Base64 形式只要有一处不一致，症状就是"口令明明对却登不上"，
   而且**永远不会报错**。集中到一处，才可能用固定向量把它钉住。

链值由 `src-tauri/src/otp.rs` 的 `otp_compute` 命令完成，单测里有与 Python / C# 对齐的固定向量
（同口令、同盐、同迭代、同 `k` → 逐字节相同的 Base64）。**参数名全部小写**，所以前端 `invoke` 的键
与 Rust 形参一一对应，不存在 camelCase 转换的余地；返回结构由 `serde(rename_all = "camelCase")` 固定为
`{ code, nextR, nextHead, elapsedMs }`。

**客户端怎么决定走哪条路 —— 本地提示（hint）**：

`login/challenge` 对"有链 / 无链 / 不存在"返回**逐字相同**的参数（§4 的防枚举要求），
所以客户端**无法**从响应里分辨该走哪条路。而两条都试一遍是不行的：链值失败会计一次登录失败，
再走口令失败又计一次，用户打错一次口令就被记两笔、三笔锁号。

于是客户端在 `localStorage` 里记一个**非机密**的提示：这个账号上一次见到的状态是有链 / 没链。
它只决定"先试哪条路"，服务端的判断永远优先。提示的三个来源都是**直接证据**：

- 链值登录成功 ⇒ 有链；
- 登录成功后 `GET /api/auth/otp/status` 回 `enrolled` ⇒ 有链（这是主要来源）；
- 凭据错（`INVALID_CREDENTIALS`）⇒ 清掉提示，下一次改走口令路径。

最后一条是**迁移期的自愈出口**：提示写着"有链"而链其实没了（库回滚 / 被重建），
用户会得到一次"口令错误"，第二次就走口令路径进去了。反过来若不清，这个账号会永远停在
"口令明明对却登不上"——那是不可接受的。**P8 移除口令路径后，这条必须改成"只报错、不回退"**（§9 第 5 项）。

**回退判据刻意很窄**：只有"结构性不可用"才换路 —— 模块关闭（`OTP_DISABLED`）、
本机算不出来（`OTP_CLIENT_UNAVAILABLE` / `OTP_CLIENT_CRYPTO`）、链已用尽（`OTP_CHAIN_EXHAUSTED`）。
凡是"服务端对凭据作出了判断"的失败（口令错 / 锁定 / 冻结 / 待审核）一律**不回退**，
否则就是上面那个"一次口误记两笔"。

**挑战过期要重试、不要降级**：`OTP_CHALLENGE_INVALID` 的含义是"这张票超过 120 秒了"，
重取一次参数重算即可；若在这里回退到口令路径，等于让"慢一点"变成"悄悄降级"。

**静默续期**：`k ≤ N×5%` 时随登录提交 `nextChain { r, head }`。判据用挑战里那个 `k`（核销前），
与服务端同一个时刻、同一套整数交叉相乘（`k*100 <= N*5`），不碰浮点。

### 7.8 一个必须知道的前置条件：Tauri v2 的 ACL

应用自己用 `#[tauri::command]` 定义的命令**也要过 ACL**。没在应用清单里登记的，前端 `invoke` 会得到
`xxx not allowed. Plugin not found` —— 这句话里没有"未注册"的字眼，很容易被读成"某个插件没装"。

本项目为此付出过代价：`get_backend_url` **一直是被拒的**，而 `api/client.js` 拿不到地址时会静默回退到
同源 `/api`（页面本来就是后端托管的），于是回退后一切正常，没人发现那次 `invoke` 其实从没成功过。
直到 P7 加了 `otp_compute`（它没有"回退"这回事）才在界面级验证里暴露。

三处必须同时改，缺一不可：

| 位置 | 内容 |
|---|---|
| `src-tauri/build.rs` | `AppManifest::commands(&["get_backend_url", "otp_compute"])` |
| `src-tauri/capabilities/default.json` | `"allow-get-backend-url"`、`"allow-otp-compute"`（kebab-case、**不带 `app:` 前缀**） |
| 同一文件的 `remote.urls` | 必须含 `http://127.0.0.1:*` 与 `https://127.0.0.1:*` —— 窗口导航到的是后端地址，Tauri 把它当 **remote** 来源，只写 `windows` 匹配不上 |

## 八、二次确认的替代

### 8.1 为什么需要它

票据是 Bearer 凭据，只证明「这个会话登录过」，不证明「此刻操作的是本人」。会话有效期是小时级，其间用户可能离开。因此对**不可逆**或**影响身份与权限**的操作，需要当场再证明一次——这就是 6 处 `OperatorPassword` / `Password` 的由来。

### 8.2 替代方式：链值再认证

敏感操作前，客户端取当前 `k`、算 `x_k`、提交，服务端验证通过后签发一次性确认凭据。

选择它的理由：

- **语义对应**：原来证明「知道口令」，现在证明「持有口令」。在替代式模型里后者就是唯一的身份凭据。
- **真正提升安全**：偷到票据的攻击者算不出链值。若换成「点一下确认」的弹窗，攻击者照样能点——那只是仪式。
- **代码复用**：直接走 `OtpVerifier`，不引入新概念。
- **体验不变**：原来要打一串口令，现在点一下自动完成。

### 8.3 三个必须处理的细节

1. **链值会被两处消费**（登录与再认证）。并发时 CAS 保证唯一成功，失败方**重新取 `k` 重试一次**，而不是直接报错。
2. **再认证失败不计入登录失败计数**——它不是登录尝试。但"不计数"**不等于"不节流"**：
   若这条路上完全没有上限，它就是一条在线口令爆破通道（拿到 `R` 后猜口令、算链值、提交，
   每次猜测约一次 PBKDF2）。所以用**独立的**计数器：5 分钟窗口内失败 5 次即封这条路径 5 分钟
   （429 `OTP_RECONFIRM_THROTTLED`），**登录不受任何影响**。
   反过来把失败记进 `FailedLoginAttempts` 也不行：那等于给持票人一个"连点三次就锁住受害者"的拒绝服务。
3. **消耗配额**。每次再认证吃掉一格，续期能吸收，但审计里要能区分这一格的消耗原因
   （`OTP_CONSUME` 的报文带 `Purpose=RECONFIRM`）。
4. **换票，而不是各验一次**。六个敏感接口不各自比对链值，而是先 `POST /api/auth/reconfirm`
   换一张一次性确认凭据（绑定 `userId` + 用途 + 目标账号、TTL 120 秒、用一次即废）。
   理由见 §8.5。

### 8.4 保留一个轻量确认

删人脸、注销账号这类不可逆操作，保留「确认删除？」的一次点击。它与安全无关，纯粹防手滑。

### 8.5 确认凭据的四个实现决定

1. **验之前先删**。任何一次消费尝试都会让凭据消失，即使用途或目标不符。
   若"不符就留着"，一张凭据就能被拿去把六种用途挨个试一遍 —— 而用途恰恰是它唯一的保护维度。
   代价是"客户端把用途写错"要多确认一次（可恢复），换来的是"凭据不可能被逐项试错"（不可恢复）。
2. **三个绑定维度对外统一话术、对内分开记录**。对外永远是同一个
   `OTP_CONFIRM_REQUIRED`（补救动作只有一个：重新确认）；审计里记下具体是哪一维不符 ——
   那是排查"客户端把目标是 A 的确认拿去操作 B"的唯一线索。
3. **不落库**。凭据只活 120 秒、一次即弃，落库要额外面对过期清理与"重启后仍在"两个问题。
   代价是多实例部署时不能共享 —— 本项目 sidecar 与客户端同机、进程只有一个，这个代价为零
   （与挑战存储同一取舍）。
4. **有效期用单调时钟**。墙钟往前拨一小时就"永不过期"，往后拨一小时就"刚签发就失效"，
   两种都不是想要的语义。

**客户端从哪里取 `R` / `k` / `N`**：复用 `login/challenge`（匿名端点，对任何用户名都返回同形状的参数），
不为再认证另开一个取参接口。`/api/auth/otp/status`（P6）只回展示用的余量信息，不承担取参职责。

**已知的体验代价**：确认凭据在接口内部按**原有顺序**消费 —— 如果后续校验（用户名重名、邮箱被占用）
才失败，管理员需要重新确认一次。这与旧路径"口令要再输一次"是同构的，因此不视为退化；
若把确认校验挪到重名检查之后，就等于让未确认的会话也能探测"某用户名是否存在"。

## 九、迁移策略（P8 定稿）

**设计时**设想的是懒迁移：无链账号下次登录时走旧路径验口令、当场建链。
**P8 落地时这个设想被推翻了**：懒迁移的前提是"登录时能验证口令"，而 P8 的目标恰恰是
删掉口令验证 —— 两条要求不可能同时成立。于是迁移改由**运维工具**承担：

```
authserver.exe --rechain --username <账号> [--password <明文>]
```

* 工具用库里的旧哈希把运维输入的明文**校验一次**（这是哈希在 P8 之后唯一的用途），
  校验通过 ⇒ 建链、把 `passwordHash` 置 null（字段保留 `BsonIgnoreIfNull`，不写空串）。
* 服务启动时统计"有哈希、没链"的账号并**点名打在启动日志**（迁移是一次性的，
  而"文档写了没人读"是过渡期最常见的失败方式）。
* 全新部署没有这个问题：空库播种的 admin 直接建链，库里从一开始就没有哈希。
* 未绑邮箱的账号无法自助重置，只能由管理员用 `--rechain` 处理 —— 这是有意保留的边界。

**P8 清理清单**（设计稿原列 6 项，落地情况）：

1. ✅ 登录 / 改密 / 六处二次确认的口令分支 —— 全部删除（`PasswordHasher.Verify` 在
   Web 路径上零调用，只剩 `--rechain` 用它）；
2. ✅ `TryMigrateToChainAsync` 删除；`PasswordHashRetained` 随迁移语义一并退场
   （审计里不再出现 `OTP_MIGRATED` / `PASSWORD_HASH_UPGRADED`，`otp_p8_probe` 钉死这一点）；
3. ✅ "新旧相同"判定移到客户端（`session.js` 的 `changePassword`，抛 `PASSWORD_REUSED`）；
   服务端对该情形返回 200（见 §7.6 边界）；
4. ✅ `otp/recover` **整条删除**而不是改造成"当前链值 + 验证码"：链坏掉/用尽时算不出
   可核销的一格，这个接口只会在"不需要它的时候能用"。需求由 `reset-password`
   （邮箱验证码 + 新口令 + 整条重建）承担；
5. ✅ 客户端自愈分支删除：`chainLogin` / `chainChangePassword` 与 `usableFor`、本地 hint
   一起退场，登录只剩一条路，凭据错只报错；
6. ✅ `LoginRequest.Password` / `ChangePasswordRequest.OldPassword` /
   `CreateAccountRequest.OperatorPassword`（含批量 `BatchRequest.OperatorPassword`
   → 改为逐目标 `ConfirmTokens`）全部删除 —— "口令明文不上网"第一次在**协议层面**成立。

## 十、验证策略

### 10.1 分层

| 层 | 覆盖 |
|---|---|
| 纯函数单测 | 推进、重放、跨格、耗尽、续期阈值、恒定时间比较、`H^k` 已知向量 |
| 集成 | 登录两步、并发 CAS、续期成功与失败两条分支、迁移分流、再认证 |
| 回归 | 既有全部用例（角色 / 锁定 / 人脸 / SoD / poller / FaceId / 批量 + xUnit） |
| 手工 | 见 `docs/reports/OTP-ACCEPTANCE.md` |

### 10.2 关键断言

1. 同一格提交两次，第二次必拒。
2. 相邻格（`x_{k±1}`）提交必拒。
3. `k = 1` 用尽后拒绝，且返回「需重建」而非「凭据错误」。
4. 并发两请求同交一格，恰好一个成功。
5. 续期写失败时，本次登录仍成功、`k` 仍按旧链递减。
6. 未知用户名的 challenge 响应与正常响应逐字一致。
7. 迁移后 `PasswordHash` 为空，链可用。
8. 再认证失败不改变 `FailedLoginAttempts`，**但会被独立节流**（第 6 次 429），且登录照常。
9. （P8 翻面）六处端点**不受理口令**：带口令不带票一律 401 `OTP_CONFIRM_REQUIRED`，
   且不计入登录失败计数（`otp_p5_probe` §8）。
10. 改密 / 重置 / 恢复之后：**新口令算出的格能登录，旧口令算出的格不能登录**。
11. 注入重建失败（MongoDB 集合校验器）：改密整体失败、**口令哈希逐字节未变**、链未动、下次正常。

## 十三、决策记录

**为什么是替代式而不是第二因子。** 叠加会要求用户持有两个秘密，而本系统已有人脸因子占据「第二步」，语义重叠。替代式让秘密保持为一个（口令），且服务端彻底不存口令派生物。

**为什么客户端不存 `k`。** 多设备会让本地缓存过期，产生「明明是对的却登不上」的故障，且难以归因。`k` 由服务端下发，代价是多一次往返（同机，可忽略）。

**为什么链状态独立集合。** 见 §5.2。

**为什么不做跳号容忍。** 同机部署几乎不丢包，容忍只会把首轮冒用的窗口放大 j 倍。

**为什么保留轻量确认弹窗。** 它不提供安全性，只防误触；不可逆操作用户会心疼。

## 十四、口径

1. 收益是「**数据库被拿走 ≠ 可冒用**」，**不是**「口令泄露也安全」——得到口令的人可以自己算链值。
2. 一次性口令**不防实时中继钓鱼**；能挡的是历史值重放。
3. 链的「一次性」是**有配额**的，配额由静默续期维护。
4. 服务端不持有口令，因此 `v` 可以不加密——与 TOTP 必须加密种子形成对照。
5. 抗离线爆破依赖 PBKDF2；若去掉它，本方案在拖库场景下劣于现状。
