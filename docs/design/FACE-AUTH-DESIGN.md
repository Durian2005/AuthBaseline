# 人脸认证接入设计（AuthBaseline）

> **状态：D1 已定稿**（"登录第二因子、账号级可选启用"，见 §六 末与 §十三）；D2 / D3 / D4 待拍板。**本文不含任何已实现内容。**
> 参考资产：本地参考项目 `<参考项目本地目录>`（仓库 `Durian2005/FaceLogin`）—— 已完成"注册 / 口令登录 / 人脸 1:1 登录 / 动作挑战活体 / 哈希链审计 / 一键启动与 PyInstaller 打包"。
> 本文回答四件事：**能不能接**、**接完长什么样**、**分几步做**、**哪些决定要你拍板**。

---

## 一、结论先说

**可行，而且属于"低成本高收益"** —— 人脸项目里真正值钱的算法资产（YuNet 检测 + SFace 特征 + 5 点姿态动作挑战 + 阈值评测口径）可以近乎原样复用；而 AuthBaseline 已经具备接入所需的全部**底座**：统一审计出口、服务端会话票据、失败锁定与双时钟、角色权限出口、Tauri sidecar 打包链路。

但有 **一条硬前提** 和 **一条必须先承认的架构差异**，写在最前面，因为它们直接决定方案形状：

| # | 事项 | 说明 |
|---|---|---|
| ⚠️ 前提 | **采集端必须留在服务端** | FaceLogin 的安全性建立在"后端进程自己持有摄像头"之上。一旦改成"浏览器采集 → 后传特征"，攻击者可以完全不碰摄像头，直接伪造一个特征向量提交 —— 活体挑战形同虚设。详见 §四。 |
| ⚠️ 差异 | **生物特征不能像口令那样单向哈希** | 口令用 `bcrypt(HMAC(pepper,pwd))` 单向存储，验的时候重算比对；人脸必须**解密后算余弦相似度**，所以模板只能做**静态加密**（可逆），不能做单向变换。这是架构性差异，答辩时会被问到，必须口径一致：**"口令是不可逆存储，人脸模板是加密存储 + 失败即拒"**，不要说成人脸也"哈希"了。 |

## 二、两个项目的现状对照

| 能力 | FaceLogin（Python） | AuthBaseline（C#） | 接入方式 |
|---|---|---|---|
| 人脸检测 | YuNet ONNX（228 KB） | 无 | **移植**（算法/模型可直接搬） |
| 人脸特征 | SFace ONNX（37 MB） | 无 | **移植** |
| 特征比对 | 余弦相似度，默认阈值 0.5 | 无 | 移植；阈值建议沿用并复核 |
| 活体反欺骗 | 服务端随机动作挑战（转头/抬头/低头），5 点姿态代理值 + 相对基线判定 | 无 | **移植**（纯数学，无额外模型） |
| 摄像头采集 | 服务端 `cv2.VideoCapture` + MJPEG 推流 | 无 | **重建**（这是 §四 的核心） |
| 口令存储 | Argon2id / scrypt | `pepper + BCrypt`（`v2$`） | 不涉及，各自保留 |
| 失败锁定 | 计数 + 锁定截止时间（同一记录） | 3 分钟窗口 + **双时钟** `TimeGuard` | **复用 AuthBaseline 的**，不要搬 Python 那套 |
| 审计 | SQLite 哈希链（`prev_hash`/`entry_hash`） | MongoDB 分片 + 锚点哈希链，**字段锁死** | **复用 AuthBaseline 的**，见 §八 |
| 会话 | Flask session cookie | **服务端票据哈希** `Authorization: Bearer` | 复用 |
| 角色/职责分离 | 无 | `UserRole` 四值互斥 + `UserRoles` 唯一出口 | 复用（人脸数据的处置权限挂在这套上） |
| 前端 | Flask Jinja 模板 + 原生 JS | Vue 3 + Pinia + Tauri v2 | **重写**（只借交互流程，不搬代码） |
| 桌面打包 | PyInstaller 单文件 | Tauri + 单 sidecar，NSIS | 复用现有链路 |

> **一句话**：借的是**算法与安全设计**，不是借代码结构。两套项目的存储层、会话层、审计层完全不同，强行缝合只会变成屎山。

## 三、三条硬约束（决定了设计形状，不是可选项）

### 3.1 审计哈希链的字段被锁死 → 只能加"值"，不能加"列"

`AuditService.ComputeHash()` 把 13 个字段 + `SHA256(request)` + `SHA256(response)` 拼进链。这意味着一件很具体的事：

- ✅ **可以**新增 `AuditAction` / `AuditReason` 常量（它们只是"字段取值"，不影响既有记录的验算）
- ✅ **可以**把任意人脸细节（相似度、活体诊断量、动作、模板版本）塞进 `request` / `response` 的 JSON 袋
- ❌ **不可以**给 `AuditLog` 加新属性（会让全部历史记录验算失败，链立刻报断裂）

这条约束**不是障碍**——它恰好推着我们把"人脸事件"设计成一等的、可检索的动作码，而不是一堆野字段。

### 3.2 认证入口唯一：人脸只能挂在登录上，或做一个并列入口

现有 20 条对外接口中，**只有 `/api/auth/login` 会签发票据**。任何新增的"人脸登录"若也签发票据，就等于开第二个认证入口 —— 两条路径的安全策略（锁定计数、沉睡记录、哈希升级、时钟背离留痕）必须**逐条对齐**，否则会出现"从人脸这条路进来就不算 lastLoginAt"这类静默漏洞。

**结论：人脸不新开认证入口，而是作为 `/api/auth/login` 的第二阶段。**（§六）

### 3.3 生物特征不可撤销 ⇒ 模板保护级别必须高于口令之外的任何数据

- 口令泄露 → 改一个口令即可撤销
- 人脸泄露 → **永久不可撤销**，且用户无法"换一张脸"

现状 FaceLogin 的做法是"只存特征、不存照片"，这是必要条件但**不充分**：特征本身足以重建身份（特征重放），且特征分布空间远小于照片空间，暴力搜索比口令容易得多。

**本设计的立场**：模板必须**静态加密**存储，密钥不得与库同处。见 §七。

## 四、最关键的设计前提：采集端放在哪

人脸项目最容易被忽略、但最要紧的一点：**它把 `cv2.VideoCapture` 放在后端进程里**。于是"这三帧画面确实是摄像头拍的"由服务端自己见证，活体挑战才有意义。

搬到 AuthBaseline 时，有两条路：

| | 方案甲：**服务端采集**（与 FaceLogin 同构） | 方案乙：浏览器采集 |
|---|---|---|
| 谁开摄像头 | AuthServer（OpenCvSharp `VideoCapture`） | WebView2（`getUserMedia`） |
| 前端看到什么 | 后端推的 MJPEG 预览 / 单帧轮询 | 原生 video 元素 |
| 活体挑战判定者 | 服务端直接采样判定（可信） | 服务端只能从"客户端送来的帧序列"里判定 |
| 攻击面 | 前端无法伪造画面 | ⚠️ **特征/帧注入**：攻击者绕过 UI 直接 POST 一个特征向量，全程不开摄像头。活体挑战降级成"客户端自觉" |
| 实现代价 | 需新增视频预览接口 + C# 摄像头依赖 | 前端简单，但安全模型降级 |
| 与 Tauri 的冲突 | 只有一个进程开摄像头，无冲突 | 若两端都想开，会抢设备 |

> **建议走方案甲。** 若因为"想让前端预览更顺滑"而选乙，必须同时补一道**服务端见证**机制（例如服务端自己对同一时刻发起一次被动采样核对），否则这个功能的威胁模型会从"反照片攻击"退回到"什么都防不住"。**这条不能省，也不能在文档里含糊过去。**

## 五、推理引擎落点：三个方案

方案甲确定了"服务端采集"，接下来是"用哪套代码做人脸计算"。

| | **A · C# 原生**（AuthServer 内，OpenCvSharp + ONNX） | **B · Python 算法 sidecar** | **C · 前端 WASM** |
|---|---|---|---|
| 复用度 | 中：算法要按 `face.py` 重写，但可 1:1 照抄姿态/比对/活体判定逻辑 | **高**：`face.py` / `liveness.py` 几乎原样复用 | 低：等于换引擎（MediaPipe 与 YuNet/SFace 不通用） |
| 依赖注入 | NuGet：OpenCvSharp4 + runtime（含 native dll，约 +60~100 MB） | 第二个 sidecar 可执行文件（PyInstaller + opencv-headless，约 +150~200 MB） | 零后端依赖，但模型资源（10~30 MB）要进 wwwroot/dist |
| 进程模型 | 单进程（与现状一致） | 双进程：Tauri 拉起两个 sidecar，或 AuthServer 按需拉起人脸服务 | 单进程 |
| 摄像头 | AuthServer 直接持有 | 人脸 sidecar 持有，AuthServer 通过内部 HTTP 取预览/结果 | ❌ 与方案甲冲突，仅适用于方案乙 |
| 失败面 | ONNX 后处理（YuNet 的 decode/NMS）要自己接；**`FaceDetectorYN` 在 OpenCvSharp 里的可用性需先验证（Stage 0）** | Python 侧已全部验证过 | CSP 需放开 `wasm-unsafe-eval`；WebView2 下 WASM 性能需实测 |
| 授权 | ⚠️ 模型沿用 FaceLogin 的 YuNet/SFace，**license 文件要一起搬**（`models/LICENSE_*.txt`） | 同 | MediaPipe 是 Apache-2.0，但换了引擎 |
| 打包风险 | 低（现有 `publish → sync:sidecar → tauri build` 链路不变） | 中（多一个 sidecar 的 md5/生命周期/端口管理） | 低 |

**推荐：优先 A，退路 B。**
- 选 A 的理由：保持"单 sidecar、单进程"的现有形态，审计与策略全部在 C# 一处收口，不引入新的进程生命周期问题（现状已知 sidecar 的坑已经踩完一遍）。
- 什么时候改选 B：Stage 0 验证发现 OpenCvSharp 的 `FaceDetectorYN` / `FaceRecognizerSF` 不可用（版本缺失或行为不符），而自己实现 YuNet 后处理成本过高时 —— 此时 B 是"零算法移植"的务实选择，代价是第二个进程。
- **C 只在方案乙（浏览器采集）下才成立**，与推荐路线冲突，列为存档备选。

## 六、认证流程：口令 + 人脸（两阶段）

人脸作为**第二因子**，不替代口令。（为什么不做单因子：SFace + 动作挑战的口径是"轻量反欺骗，不等于完整活体"—— FaceLogin 的 README 与 THREAT_MODEL 就是这么写的，接手时不能反向夸大。）

```
┌─ 客户端 ─────────────────────────────────────────────────────┐
│ 1. 输入用户名 + 口令                                          │
│ 2. POST /api/auth/login {username, password}                 │
│      ├─ 未录入人脸 → 现状行为，直接签发 ticket（向后兼容）      │
│      └─ 已录入人脸 → 不签发 ticket，返回                       │
│           { faceRequired: true,                       │
│             faceChallenge: "<一次性 token>",           │
│             action: "left|right|up|down"  }            │
│ 3. 界面提示："请把头转向你的左侧"                              │
│ 4. POST /api/auth/face/verify {challengeToken}               │
│      （服务端自己采样摄像头判定动作是否真实发生）                │
│      ├─ 通过 → 签发正式 ticket                                │
│      └─ 不通过 → 计一次失败（复用锁定窗口），返回剩余机会        │
└─────────────────────────────────────────────────────────────┘
```

**三个必须讲清楚的安全细节：**

1. **`faceChallenge` 不是票据。** 它是登录**中间态凭证**，一次性、90 秒 TTL、只对"这一次登录尝试"有效，**不能用于调用任何其他接口**。它必须与 `SessionService` 签发的正式 ticket 是两套东西、不可互换 —— 否则"口令过了但人脸没过"的人就能拿着它去调别处。
2. **挑战的"题面"不保密，安全性来自"随机 + 新鲜 + 一次有效"。** 这与 FaceLogin 的注释口径一致（攻击者可以知道指令，但对不上实时画面）。
3. **活体失败是否计入锁定次数：建议计入。** FaceLogin 里活体失败不消耗次数（避免正常用户被动作判定误伤）；但 AuthBaseline 是安全实验场景，"明明是欺骗尝试却不计数"在威胁模型上说不通。取舍理由要写进文档，答辩时这是个好问题。
   - 折中做法：把"未检测到人脸/光线不足"这类**质量问题**与"动作不匹配/人脸跳变"这类**欺骗信号**分开 —— 前者不计、后者计。这需要在 `AuditReason` 里分开两个码（见 §八）。

### 可选启用：语义、引导时机与降级通道

**决定（D1，已定稿）**：人脸作为**登录的第二因子**，**账号级可选启用** —— 已注册用户可自行添加，新注册用户可跳过。

**口径**（这一条必须守住，否则验收时会说不圆）：

- ✅ 可以说："系统**支持**第二因子，账号级可选启用，管理角色可配置为强制。"
- ❌ **不可以**说："系统启用了双因子认证。"
- 原因：只要库里存在**没录人脸**的账号，那些账号的口令就是唯一防线，系统整体安全性等于最弱账号。这与哈希链那条"只说局部断点、不说不可篡改"是同一类口径问题。

**由此带来一条必须堵的降级通道**（人脸可选 ⇒ "不录/删掉"就是降级）：

| 通道 | 风险 | 堵法 |
|---|---|---|
| 已登录会话里**删除人脸模板** | 攻击者拿到一个有效会话，删掉模板，该账号从此退回单因子 | 删除 / 更换人脸**须重新输入口令**确认（沿用 `create-account` 的二次口令模式）；记独立高优先级审计，不并入普通账号操作 |
| **管理员重置他人人脸** | 等于把别人降级成单因子 | 走 `UserRoles.CanBeManagedBy`；高优先级审计留痕；**文档承认这条权力存在，不宣称已阻止**（与已承认的"SoD 可被 Admin 绕过"同类） |
| **注销账号** | 模板是生物特征，留孤儿 = 生物特征滞留 | `DELETE_USER` 必须**在同一动作内清理** `FaceTemplates` 中的记录（现在注销是硬删且不可逆） |

**引导时机（别在注册表单里嵌摄像头）**：

- ❌ 注册表单里录入人脸 —— 注册时**还没有登录态**，采集接口会落在**未鉴权面**；叠加"采集端必须在服务端"（§四），等于开一个"未登录就能打开摄像头"的口子。
- ✅ 注册成功 → 立即进入一个**可跳过**的人脸引导页（此时已持有票据）。录入率接近"注册时录"，但不扩大未鉴权面。
- ✅ 已注册用户：在 `AccountView` 内自行添加 / 更换 / 删除。

**强制策略留一个开关位**：配置项 `Face:Enforcement = off | optional | required-for-roles`。

- 第一版**只实现 `optional`**，但把配置项位置留出来，避免以后改架构。
- 建议管理类角色（Admin / UserAdmin / AuditAdmin）可配置为 `required` —— 数量少、价值最高、录入成本几乎为零，是性价比最高的一档强制。

**反过来说，为什么不放在"找回密码"上**（这条决策的理由留档，答辩时会被问）：

找回密码的入口 = **账号接管入口**，能通过它的人就能改口令，所以它必须**至少和登录一样强**。而人脸在四个维度上弱于口令：① 它不是秘密（脸是公开可观察的）；② FAR 非零且永久存在；③ **泄露不可撤销**（口令泄露改口令即可，脸改不了）；④ 按本项目自己的口径，活体只是"轻量反欺骗"，防不住举着手机实时配合动作。

于是会推出两个不能接受的结论：**攻击者不再需要知道口令，只需要你的脸**；以及**登录判错 = 进不去（轻），找回判错 = 账号被接管（重）**——同一个 FAR 放在这两个位置，后果差一个数量级。"没绑邮箱的账号无法自助找回"这个缺口，正确的答案是**一次性恢复码**（可撤销、熵可控、零误识率、可离线保存），或管理员重置，不是人脸。

## 七、数据与存储

### 7.1 新集合 `FaceTemplates`（不动 `Users` 结构）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | |
| `userId` | string | 关联 `Users._id` |
| `cipher` | Binary | **加密后的**特征向量（AES-GCM：nonce + tag + ct） |
| `dim` | int | 特征维度，随向量一同存储（FaceLogin 的 `pack()` 就是这么做的，读回时校验） |
| `createdAt` | DateTime | 录入时刻 |

- 索引：`{ userId: 1 }`（每人最多保留 N 个模板，超出淘汰最旧 —— 沿用 FaceLogin 的 `MAX_TEMPLATES_PER_USER = 8`）
- **不入 `Users` 文档**：登录路径上每次都要判断"这账号有没有人脸"，放在独立集合里配合 `{userId:1}` 索引是一次极轻的查询；塞进 `Users` 反而会让每次读取用户都拖着一个特征数组。
- 若实测发现登录路径多一次查询不可接受，**再**在 `User` 上加一个 `faceEnrolledAt` 冗余标记（`User` 不在哈希链内，加字段是安全的）—— 但先不要预支这个复杂度。

### 7.2 模板加密（§3.3 的落点）

- 密钥来源：与 `pepper` 同级的**本机密钥**（`PepperProvider` 已有一套 DPAPI + 文件存放的成熟做法，可平行扩展一份 `FaceKeyProvider`，或复用 pepper 派生）。
- ⚠️ 与 pepper 一致的红线：**密钥丢失 = 全部人脸模板不可用**（后果是"重新录一次"，不是"泄露"，这一点比口令温和，可以在文档里明说）。
- 明说边界：这是**静态加密**，防的是"库文件被拿走"；防不了"进程被注入/调试器附加"。不要写成"模板不可逆保护"。

## 八、审计扩展（增量清单）

只加**常量与 JSON 袋内容**，`AuditLog` 一行不改（§3.1）。

### 8.1 新增 `AuditAction`

| 常量 | 时机 |
|---|---|
| `FACE_ENROLL` | 本人录入人脸模板成功 |
| `FACE_ENROLL_FAILED` | 录入被拒（质量问题 / 活体未过 / 达到模板上限） |
| `FACE_LOGIN_REQUIRED` | 口令已过、要求第二因子（中间态，留痕便于重放攻击分析） |
| `FACE_LOGIN_SUCCESS` | 人脸通过，签发票据 |
| `FACE_LOGIN_FAILED` | 人脸未过（相似度不足 / 活体未过 / 无人脸） |
| `FACE_TEMPLATE_DELETED` | 本人删除自己的模板 |
| `FACE_TEMPLATE_RESET` | 管理员重置他人模板（走 `CanBeManagedBy`，与注销同一权限出口） |

### 8.2 新增 `AuditReason`（**建议把"质量问题"与"欺骗信号"分开**）

| 常量 | 语义 | 计入锁定次数 |
|---|---|---|
| `FACE_NO_TEMPLATE` | 该账号未录入人脸 | —（不应发生，是异常路径） |
| `FACE_MISMATCH` | 相似度低于阈值 | ✅ 计 |
| `FACE_LIVENESS_FAILED` | 动作挑战未通过 / 人脸跳变 | ✅ 计（欺骗信号） |
| `FACE_NOT_RETURNED` | 动作完成但未回正对镜头 | 建议不计（交互误伤） |
| `FACE_NO_FACE` / `FACE_LOW_QUALITY` | 没人脸 / 离太远 / 光线不足 | ❌ 不计（质量问题） |
| `FACE_CHALLENGE_INVALID` | 挑战 token 过期 / 复用 / 不匹配 | ✅ 计（明确的绕过尝试） |

### 8.3 进 `request` / `response` JSON 袋的内容

相似度、阈值、动作指令、姿态诊断量（`yaw/pitch` 区间、耗时、采样数）、模板版本计数。
⚠️ **特征向量本身绝不进审计**（它是生物特征本体，且审计链是"反复翻阅"的数据）；⚠️ **画面绝不进审计**。

## 九、接口增量清单

现对外 **20 条**；本设计新增 6 条以内，全部落在既有四个 Controller 的**域边界**内。
（下表是**设计期**的候选清单，实际落地路由见本节末尾「实现落地」。）

| # | 方法 | 路径 | 鉴权 | 归属 | 说明 |
|---|---|---|---|---|---|
| 21 | POST | `/api/auth/face/verify` | 无（凭 `faceChallenge`） | AuthController | 登录第二因子：服务端采样 + 判定 + 签票 |
| 22 | GET | `/api/auth/face/challenge` | 无 | AuthController | 可选：单独取挑战（若希望登录前先出题） |
| 23 | GET | `/api/auth/face/camera` | 无 | AuthController | 预览流（MJPEG 或单帧），供登录页显示取景框 |
| 24 | GET | `/api/account/face` | Authenticated | AccountController | 查询本人录入状态 / 模板数 / 录入时间 |
| 25 | POST | `/api/account/face` | Authenticated | AccountController | 本人录入 / 更换人脸 |
| 26 | DELETE | `/api/account/face` | Authenticated | AccountController | 本人删除人脸模板 |

要点：
- `/api/auth/face/*` 属于**未鉴权面**（登录前），与 `/api/auth/transport` 同类。这有一个**已知且必须复述**的代价：未鉴权接口可被任意本地页面触发，当前唯一缓解是"仅绑环回"。人脸接口比 transport 更敏感（摄像头被远程打开是隐私事件），**这条要在威胁模型里显式登记**。
- 接口 27 的权限**不加新规则**，直接复用 `CanBeManagedBy` —— 与"重置口令""注销"同源，新增角色时不会漏改。
- 路由前缀保持"只动文件边界、路由一字未变"的既有约定：人脸认证入口在 Auth 域，自助在 Account 域，管理在 UserAdmin 域。

### 实现落地（最终对外路由，**共 27 条**，新增 7 条）

设计期的候选清单在实现时做了三点收敛：**① 预览接口延后到第二阶段才补**（见下方 #27 与"预览回归"小节，
理由不是"不该做"，而是"要先把门禁想清楚"）；**② 录入拆成两步**（先凭口令取一次性挑战、再凭挑战提交采集），
使"口令闸门"与"采集动作"解耦；**③ 不用 `DELETE` 动词**，与既有接口统一为 `POST`。

| # | 方法 | 路径 | 鉴权 | 归属 | 说明 |
|---|---|---|---|---|---|
| 21 | POST | `/api/auth/login/face` | 无（凭一次性挑战 token） | `AuthController` | 登录第二因子：服务端采样 + 判定 + 签票。请求体**只有 token** |
| 22 | GET | `/api/auth/face` | 需票据 | `AccountController` | 本人人脸状态（已录 / 模板数 / 录入时间 / 引擎是否就绪）。只读，**不写审计** |

| 24 | POST | `/api/auth/face/enroll/complete` | 需票据（凭挑战） | `AccountController` | 录入第二步：凭挑战完成采集与加密入库 |
| 25 | POST | `/api/auth/face/delete` | 需票据 + **口令** | `AccountController` | 删除本人模板（真删） |
| 26 | POST | `/api/auth/reset-face` | 用户管理员 | `UserAdminController` | 重置他人模板，复用 `UserRoles.CanBeManagedBy`（含自我豁免） |
| 27 | GET | `/api/auth/face/preview` | 匿名（凭**一次性挑战 token**） | `AuthController` | 识别画面：一帧服务端采集并画好框的 JPEG；状态走 `X-Face-State` / `X-Face-Score` 响应头。**只出图像，不下发关键点坐标** |

> ⚠️ 与设计期表格的对应关系：#22 取代原 22/23，#24 对应原 24，#25 对应原 25，#23+24 取代原 25，#26 取代原 27，
> #27 是设计期 #23"预览流"的**落地形态**（形状变了，理由见下）。
>
> ⚠️ 设计期登记的那条威胁（"`/api/auth/face/*` 是未鉴权面，可被任意本地页面触发"）在实现中**依然成立**，
> 但被削掉了一半：#21 与 #27 都需要**一次性挑战 token**（挑战只由口令通过后的 `/api/auth/login`、
> 或本人重新输过口令的 `/api/auth/face/enroll` 签发，且一次性、有 TTL、用途绑定），
> 因此不再是"任何本地页面都能打开摄像头"。
> 缓解手段仍只有"仅绑环回" + 挑战门禁，**答辩时照旧登记，不要宣称已解决**。

#### 预览回归（#27）：为什么"去掉"又"加回来"

设计期写下"去掉摄像头预览接口"时，给出的理由是**采集全程在服务端，前端不持有画面流，CSP 与隐私两头都省**。
这条理由在落地上被拆成了三句，只有第三句真的成立：

| 设计期的担心 | 是否真的挡路 | 落点 |
|---|---|---|
| 采集端必须在服务端，否则可提交伪造特征 | **不挡**。它防的是"前端**上送**画面/特征"，不是"前端**观看**" | 接口形状不变：请求体仍然只有 token，没有画面也没有特征 |
| 前端自己开摄像头会与后端抢设备（DSHOW 下第二次打开通常失败） | **挡**。所以**绝不能让 WebView2 自己开摄像头** | 画面一律由服务端出；前端只做显示 |
| 后端无鉴权地推画面 ⇒ 本机任何页面都能拉摄像头流 | **部分挡**。这是"预览必须有门禁"，不是"不能有预览" | #27 的门禁**绑在挑战上**：过期 / 被消费 / 采集结束即失效 |

实现上的三条硬约束（改这个功能前先读）：

1. **帧在服务端画。** 5 个关键点属于生物特征，一旦下发就等于把特征面暴露出去。
   服务端画成框再编码成 JPEG 下发，前端手里只有**可视化结果**，没有坐标。中文措辞由前端用 HTML 叠加
   （OpenCV 内置 Hershey 字体不含汉字）。
2. **摄像头生命周期跟着门禁走。** `FacePreviewService` 的后台取帧循环在"没有有效 token"时立刻
   `Close()` 释放设备 —— 预览窗口一结束，摄像头不会留在打开状态。
3. **采集期与预览期互斥。** 正式采集（`RunChallenge`）期间预览循环**停手**，画面改由采集循环推
   （它读到的就是判定用的那一帧）。两边各读一半帧会把 14Hz 采样砍半，是能直接把挑战判失败的。

> ⚠️ 前端渲染走 `fetch` + `canvas`，而不是 `<img src>`：桌面壳 CSP 的 `img-src` 只放行
> `'self' / asset: / data:`，既不含后端源也不含 `blob:`；而 `connect-src` 是放行后端的。
> 这样**不必为这个功能给 CSP 开任何新的口子**，顺带还能读到响应头里的检测状态。
> 跨源时 `X-Face-State` / `X-Face-Score` 必须由 CORS `WithExposedHeaders` 显式放行，否则 JS 读不到。

## 十四、验收要点（写在文档里，是为了让实现不跑偏）

1. **"拿 faceChallenge 调任何受保护接口"必须失败** —— 这是第二因子机制成立的最小证明。
2. **未录入人脸的账号，登录行为与改造前逐字一致** —— 向后兼容不是"基本一致"。
3. **人脸失败确实计入 3 分钟窗口，且拨钟不能解锁** —— 复用双时钟判定，不能自建一套。
4. **审计里能一条查询捞出"全部人脸相关事件"，且链完整** —— 校验接口对新增动作码无感。
5. **审计与截图里都不出现特征向量、不出现画面** —— 跑 `privacy_scan.py`。
6. **用一张照片 + 一段预录视频重放挑战，必须被拒** —— 这是功能存在意义的证明，不是可选项。
7. **删除 / 更换人脸必须要求重新输入口令**，且审计能区分"本人删除"与"管理员重置" —— 前者是自助，后者是处置，混在一起会让审计员看不出一致性被削弱的过程。
8. **注销账号后 `FaceTemplates` 中不留任何该用户的记录** —— 生物特征不允许有孤儿。
